## 0. 一页决策版

### 0.1 三句话结论

1. **工程能力已经超出这个项目当前的使用规模。** 22 个质量门脚本、35 个变异、确定性可行性引擎、证据双轴、离线执行闭环——这套地基在同体量项目里罕见。但地基之上还没有人住：相册 0 张照片、笔记 1 篇、626 个点位里只有 38 个真正"可信"、0 个真实用户、0 个埋点、0 个分享入口。
2. **市场窗口是真的，而且有时限。** 俄罗斯对华免签延至 2027 年并可能永久化；2026 年 1–5 月中国赴乌兹别克斯坦 178,121 人次、同比 +78%；中亚航线中国客源暴涨。与此同时，Booking Holdings 明确说所有 AI 助手带来的间夜"显著低于 1%"且连续几个季度没动，OpenAI 也在 2026-03 撤回了对话内结账。**规划已被商品化，交易闭环还早，中间那段"可信 + 可执行 + 可协作"没人认真做。**
3. **下一个 12 个月的正确目标不是"补齐旅行闭环的所有功能"，而是"用一条最小价值链证明护城河"。** 价值链是：莫斯科一个城市做到事实可信 → 一次真实执行 → 一份同行者能直接用的离线胶囊 → 一个可分享、可被搜索到的创作者路书 → 一条能测量的回流。跑通它，平台叙事才成立；跑不通，就老实做一个"个人 + 小圈子"的精品工具，也比假装平台好。

### 0.2 战略定位

> **面向中国独立旅行者的「俄罗斯 / 中亚 行程作业系统」：把不可信的攻略变成可核验的事实，把计划变成能离线执行的"今天"，把一次旅行变成可复用的路线资产。**

**它不是什么：**

| 不是 | 为什么不做 |
|---|---|
| 又一个 AI 行程生成器 | 生成能力已归零成本。ChatGPT、Gemini、Wanderlog、Mindtrip 都能在 30 秒内产出一份"看起来不错"的行程。再做一个只会被比较"谁的文案更好"。 |
| OTA / 预订平台 | 行业数据已经证明 AI 带来的预订 <1%，且支付环节是所有玩家的共同刹车点。我们没有任何库存或价格优势。 |
| 全球攻略库 | 626 个点位分散在 9 个城市，是广度幻觉。数据护城河只能靠深度一城一城挖。 |
| 社交网络 | 没有冷启动用户量的社交产品等于许愿。协作只做"一次旅行内的最小闭环"。 |
| 浏览器 Agent 代订 | 实测成功率 <50%，CAPTCHA 即放弃，且合规风险高。行业已经用两年时间证明这条路走不通。 |

### 0.3 三个旗舰赌注

| # | 赌注 | 一句话 | 为什么是护城河 |
|---|---|---|---|
| **A** | **证据链编译器**（Trip Compiler with Proof Chain） | 不只给行程，给"行程 + 每条结论的证据状态 + 失效日期 + 待核验清单" | 需要长期、枯燥、可累积的人工研究。AI 生成不了"2026 年 11 月特列季亚科夫周一闭馆"这种事实，只能引用我们的。 |
| **B** | **离线胶囊 + Today 2.0 + 行前压力测试** | 一个文件发给同行者，飞行模式也能走完一天；出发前先演练 5 种坏情况 | 现场是 OTA 和 AI 都不愿去的角落。做过一次真实旅行的人才知道"没网 + 同伴不装 App"有多常见。 |
| **C** | **Guest-first 协作 + 亲证路线图 + MCP 分发** | 免注册链接加入、认领任务、投票；走过的路段变成第一方数据；让 ChatGPT/Claude 成为我们的分发前端 | 网络效应 + 数据回流 + 新渠道红利。别人抄功能容易，抄"12 次实测的中位通行时间"很难。 |

### 0.4 v4 → v5 的关键差异

| 维度 | v4（2026-11-01） | v5（本文） | 理由 |
|---|---|---|---|
| **主线** | 先稳定化，再完整闭环，再创新 | 四条轨道并行：信任 / 现场 / 分发 / 平台 | v4 把分发放到 P7 之后，等于把"有没有人用"排到最后 |
| **验证方式** | 站长本人 2 天实地或高仿真 | 站长 + **至少 2 位非站长**真实使用；有埋点 | n=1 的现场验证会系统性高估产品完成度 |
| **内容/数据** | 按"城市全量覆盖"补 | 按"莫斯科 Top 60 决策就绪"补，**工程周与内容周 1:1 配比** | 全量覆盖在单人产能下永远补不完，且大部分点位没人去 |
| **分发** | P7 才考虑 | P3 就开始：SEO 落地页、分享页、OG、guest 链接、MCP | 没有获客就没有反馈，没有反馈就没有产品判断 |
| **时间模型** | 列为"多城扩张前补齐" | 提前到 P1，作为预订实体的前置条件 | 时区/跨午夜是预订和航班的地基，越晚改越贵 |
| **协作** | P6，实时多人协同明确不做 | 提前到 P3（guest 链接）+ P4（Member），**只做异步**，仍不做实时协同 | 同行者对齐是真实痛点，且不需要 WebSocket |
| **商业化** | 无 | 四假设排序验证，先卖"定制行程服务" | 单人产能 + 高信任度，天然适合服务型变现 |
| **创新组合** | P7 列 6 项，无门槛 | 收敛为 3 个旗舰 + 明确否决清单 | "6 项创新"等于 0 项创新 |
| **节奏** | 阶段串行，18 个月 | 26 周主干 + 常态运营，季度复盘 | 单人 10–15h/周，串行大计划必然延期 |

### 0.5 90 天最重要的一件事

> **把莫斯科前 40 个高频点位的事实补齐（6 个月内扩到 60），并让 3 个真人用一份离线胶囊走完一天。**

不是拆 `plan.js`，不是接 MCP，不是做费用分摊。因为如果这一件事做不成，"可信旅行作业系统"这个定位就是假的，后面所有功能都建在沙子上。

## 2. 项目现状审计

### 2.1 工程体检

| 维度 | 实测值 | 判断 |
|---|---|---|
| 前端代码 | `src/` 41 个 JS / 9,372 行；11 个 CSS / 1,412 行；10 个 HTML / 301 行 | 体量健康，但 `plan.js` 1,186 行 + `map.js` 933 行占 22% |
| 工具链 | `tools/` 57 个脚本 / 6,591 行；19 个 `test-*.mjs` | 测试投入远超同类个人项目 |
| 后端 | `api/index.php` ~600 行单文件 | 够用，但已到拆分临界点 |
| 质量门 | `npm test` 串联 22 个质量门脚本（实际 32 次命令，含 8 次城市排程）；变异测试 35/35 捕获 | 领域层覆盖扎实，UI/真机几乎为零 |
| 构建 | Vite 68–69 modules，哈希文件名，产物回写仓库根，SW 版本注入 git sha | 工程化程度高，`publish` 一处硬编码事故已修 |
| 部署 | GitHub → 腾讯云 cron ≤2 分钟 `reset --hard` | 简洁，但单点、无灰度、无回滚演练 |
| 数据 | 9 城 626 点 / 28 条动线 / 36 条交通矩阵 | 见 §2.3，广度与深度严重不匹配 |

**一句话：这是一个"基础设施 8 分、产品 3 分、内容 1 分、分发 0 分"的项目。** 不是贬低——8 分的基础设施是最难补的那部分，问题在于它被用来支撑了一个还没被验证的需求。

| Trip v2 编辑与迁移 | ● | ● | ● | ◐ | 编辑器强，手机路径未进 CI |
| 可行性引擎（双轴） | ● | ● | ● | ○ | **人工认可率从未测过** |
| 时间轴视图 | ● | ● | ● | ○ | 同上 |

### 2.3 数据深度审计（本次最硬的发现）

| 城市 | 点位 | 有坐标 | 有停留时长 | 开放日历已知 | 票价已知 | 有来源 | 动线 |
|---|---:|---:|---:|---:|---:|---:|---:|
| 莫斯科 | 278 | 277 | **43** | **17** | 8 | 43 | 7 |
| 圣彼得堡 | 96 | 93 | 93 | **0** | 0 | 0 | 9 |
| 三亚 | 89 | 86 | 89 | **0** | 6 | 0 | 6 |
| 阿拉木图 | 66 | 60 | 60 | **0** | 0 | 0 | 0 |
| 哈尔滨 | 35 | 35 | 35 | **0** | 0 | 0 | 0 |
| 叶卡捷琳堡 | 29 | 29 | 29 | **0** | 0 | 0 | 0 |
| 伊宁 | 21 | 21 | 21 | **0** | 1 | 0 | 1 |
| 其他城市 | 7 | 7 | 7 | 0 | 0 | 0 | 4 |
| 莫斯科州/近郊 | 5 | 5 | 5 | 0 | 0 | 1 | 1 |
| **合计** | **626** | **613** | **382** | **17** | **15** | **44** | **28** |

**四个必须直面的比例：**

1. **开放时间覆盖率 = 17 / 626 = 2.7%。** 而"开放时间"是可行性引擎里权重最高的硬约束——闭馆、最后入场、周一休馆，全部依赖它。
2. **"可信点位"（有坐标 + 有停留 + 有开放日历 + 有来源）≈ 38 个，占 6.1%。** 全部集中在莫斯科样板。
3. **莫斯科内部也不均衡：278 个点位只有 43 个有停留时长。** `check-city-duration.mjs` 对 8 个城市全量跑，但**莫斯科被排除在门槛之外**——因为它的全量数据补不完。
4. **实测停留时长 = 0 / 626。** 所有排程的时间假设都是估算，包括那 38 个样板点。

> **结论：`626 个点位`是内容营销数字，不是产品能力。** 真正能支撑"可信"这个卖点的，是莫斯科那 38 个点。把它们做到 60 个、每一条都有官方来源和复核日期，价值远大于再补 200 个没有开放时间的点位。

### 2.4 内容审计：产品名承诺了它没有的东西

| 资产 | 现状 | 问题 |
|---|---|---|
| `photos/index.json` | `[]` | 相册页是空壳。整个"旅行笔记"的视觉记忆层不存在。 |
| `content/notes/` | `example.md` + `index.json` | 1 篇示例笔记。首页的"N 篇笔记"统计永远不显示。 |
| UGC / 投稿 | PHP `submissions` 表 + 审核流程可用 | 有管道，无内容，无投稿者。 |
| 站点截图 | `smoke-*.png` 为 CI 产物 | 首页/README 用的仍是旧截图，与 M0/M1 后的界面不一致 |

**这是最尖锐的盲点：产品叫「牛马打工人的旅行笔记」，但代码交付的是一个行程规划器。** 名字承诺"记录与回味"，产品提供"排程与执行"。用户第一次打开会感到错位——而这种错位会在 10 秒内决定他是否留下。

### 2.5 领域模型缺口

`src/pages/trip/schema.js` 已经相当完整（Trip / Day / Item / Visit / ChangeEvent / TransitLeg），但距离"完整旅程"还缺 7 个实体：

| 实体 | 现状 | 缺了会怎样 |
|---|---|---|
| **Reservation** | `ITEM_TYPES` 有 `'reservation'`，但只是一个带时长的块：无确认号、无供应商、无取消截止、无凭证 | 无法回答"酒店订了没、几点前可免费取消" |
| **Document** | 无 | 护照、签证、保险、机票 PDF 无处安放；只能塞进笔记 |
| **Expense** | 无 | 无法结算、无法分摊、无法对比预算 |
| **Member** | 无（PHP `accounts` 只服务投稿） | 无法知道"这次旅行有谁、谁负责什么" |
| **Share** | 无 | 无法把行程给同行者，只能截图 |
| **RouteTemplate** | 无（`routes.json` 是只读静态动线） | 创作者的路书无法被 fork、无法版本化 |
| **FactRevision** | research 管线有候选校验，但无线上修订历史 | 事实改了没人知道改了什么、谁改的、依据是什么 |

> 这不是"功能没做"，是**领域模型没有为"旅行是一个多人、多凭证、有金钱、有记忆的过程"建模**。现在的模型是一个"单人、单程、无票据"的排程器。

### 2.6 时间模型缺口（会阻塞多城与预订）

| 问题 | 证据 | 后果 |
|---|---|---|
| 无 Trip 级时区 | `Trip` 无 `timeZone` 字段（`Day`/`Item` 有但可选） | 多城行程无法定义"今天是哪一天" |
| "今天"用设备时间 | `today.js:17-19` 的 `localToday()` / `localNowMinutes()` 全部读 `new Date()` | 人在北京看莫斯科行程，"今天"是北京的今天 |
| 完成动作日期走 UTC | `execution.js:135,175` `new Date(stamp).toISOString().slice(0,10)` | 东八区凌晨 00:00–08:00 完成，日期落到前一天 |
| 不支持跨午夜 | `Day.endTime > startTime` 强校验 | 18:00–02:00 的夜车/夜游/红眼航班无法表达 |
| 无绝对时刻 | `isLocalTimeValue` 只接受 `HH:MM` 或 `YYYY-MM-DDTHH:MM`，无 offset / UTC instant | 航班、火车、跨时区预订无法排序 |
| `timeZone` 被校验但不被消费 | `feasibility.js` 全文 0 处引用 `timeZone` | 时区字段目前是装饰品 |

**这不是"以后再改"的问题。** 一旦 Reservation 上线，所有预订都带绝对时刻和时区；届时再改 `Day` 窗口语义，等于重写可行性引擎和整个编辑器的落库路径。**必须在预订实体之前修完。**

### 2.7 CI 与文档的自我欺骗（最伤文化的一类问题）

项目有 `check-doc-facts.mjs` 这个很好的想法——"文档里写死的数字必须和代码一致"。但它自己漏了：

| 问题 | 证据 | 风险 |
|---|---|---|
| CI 少跑 4 个质量门 | `.github/workflows/check.yml` 未包含 `test-visit-repository.mjs`、`test-trip-execution.mjs`、`test-trip-offline.mjs`、`check-transit-matrix-anomalies.mjs` | 本地绿、CI 绿，但 CI 根本没跑最关键的三组 M0/M1 测试 |
| 校验清单一半派生、一半手写 | `check-doc-facts.mjs` 第 4 项（`npm test` 是否覆盖全部 gate）**从 `tools/` 目录派生**，很稳；第 5 项（CI 是否覆盖）却硬编码 21 个文件名 | 作者已经知道"要派生"，但只在第一处做了。这与 `publish.mjs` 的 `HTML_FILES` 硬编码是**同一个 bug 模式**，后者已经害得 `today.html` 线上 404 过一次 |
| README 页面清单漏页 | `README.md` 仓库结构写 `index/map/list/notes/album/plan/friend/account/admin`，缺 `today.html` | 新人（包括 AI）按文档理解项目会漏掉 M1 的核心页面 |
| 冒烟不覆盖 Today | `tools/smoke-test.mjs` 只探 map 与 plan | 行中最重要的页面零端到端覆盖 |
| 文档声称 > 实际 | `AGENTS.md` 第 12 行在 `npm test` 清单末尾标注「CI 同样跑」，但 CI 实际少 4 个 | "文档事实门通过"本身成了一个假绿灯 |

> **这是全项目最危险的一类缺陷：不是代码错了，是"验证系统"在骗自己。** 一个能自动发现数字漂移的机制，自己漂移了，说明它缺的不是更多规则，而是**从单一事实源派生**。

**修法（1 天工作量，收益极高）：**

```js
// tools/check-ci-parity.mjs
// 1. 从 package.json 的 test 脚本里按 && 切出所有 node tools/xxx.mjs
// 2. 断言每一个都出现在 .github/workflows/check.yml 里
// 3. 断言 check.yml 里的每个 test-*.mjs 都存在于 tools/
// 4. 反向：CI 里有但 npm test 没有的，也报出来（防止两边分叉）
```

然后删掉 `check-doc-facts.mjs` 里那个手写数组。

### 2.8 分发与可发现性：资产是隐形的

| 项 | 现状 | 影响 |
|---|---|---|
| `sitemap.xml` | **5 个 URL**（首页、map、list、notes、album），全是客户端渲染的空壳 | 626 个点位 → **0 个可被搜索引擎索引的点位页** |
| `robots.txt` | 只有 `Disallow: /admin.html` | 没有为内容页做任何引导 |
| OG / Twitter Card | **0 个页面有** | 分享到微信/小红书/Telegram 时没有标题图，点击率极低 |
| 分享 API | 全站 0 处 `navigator.share` / 剪贴板分享 | 行程只能截图传播 |
| 埋点 | 全站 0 处 analytics / beacon | 无法回答"有多少人来了、看了什么、走到哪一步走了" |
| 结构化数据 | 无 JSON-LD | AI 爬虫与搜索都无法理解"这是一个地点/一条路线" |

> **数据护城河的前提是数据能被看见。** 现在的架构是：HTML 空壳 → JS 运行时 `fetch('./data/points.json')` → 渲染。搜索引擎看到的是空 div，AI 爬虫看到的是空 div。**我们花了 3 个月积累的 626 个点位，在互联网上是不存在的。**
>
> 这是 v5 必须提前解决的事，而且技术上不难：构建期预渲染（SSG）城市页与点位页，`sitemap` 从 `points.json` 生成，OG 图用构建期 SVG → PNG。

### 2.9 商业模式：完全空白

- 无定价、无付费点、无非公开功能。
- 服务器成本极低（单台腾讯云 + SQLite），AI 用用户自带 Key（`ai-at-rest.key` 加密），**边际成本接近 0**——这是好事，意味着可以长期不赚钱地活着。
- 但也意味着：**没有任何机制告诉我们"这个东西对谁值多少钱"**。

### 2.10 诊断结论

```text
┌─────────────────────────────────────────────────────────┐
│  优化目标函数错了                                          │
│                                                         │
│  当前：最大化「系统正确性」                                 │
│        测试更全、约束更严、证据更细、边界更清楚              │
│                                                         │
│  应该：最大化「单位产能的用户价值密度」                       │
│        一个城市可信 > 九个城市都可排                        │
│        三个人真用 > 一百个功能没人用                        │
│        能被搜到 > 数据很全但藏着                             │
└─────────────────────────────────────────────────────────┘
```

每个工程决策**单独看都是对的**：统一 Visit、原子写入、双轴证据、离线优先、拒绝 CP-SAT、拒绝自动订票。但把它们放在一起，资源分配是全局错配的——**90% 的产能在打磨"系统"，10% 在创造"价值"**。

v5 的核心不是加功能，是**重新分配产能**。

### 3.2 TREK：平台化的终点长什么样

**它做对了什么**

- **166 个 ORM 实体**覆盖了旅行的几乎全部侧面：`AssignmentParticipants`、`BudgetCategoryOrder`、`BucketList`、`AssistantThreads/ToolCalls/Usage`、`AuditLog`……这是一份现成的"旅行领域实体清单"。
- **137 个控制器** + NestJS 分层 + `plugin-sdk/`（84 文件）+ addon 开关（`addons.ts`）。功能是**可插拔**的，不是堆在一个 `app.js` 里。
- **数据库纪律**：`pre-migrate-snapshot.ts`、`schema-snapshot.ts`、`known-migrations.ts`、`legacy-baseline.ts`、`durability.ts`。迁移前自动快照，schema 有基线，旧库有兼容层。
- **离线与移动端是一等公民**：`client/src/mobile`、`push/`、`managed/` 独立目录。
- **测试密度 3,219 个文件**，Sonar 质量门接入 CI。

**它的代价**

- 13,289 个文件。单人维护需要数年。
- 需要 Docker、数据库、对象存储、邮件、地图 token——**运维复杂度远超个人项目**。
- AGPL-3.0：任何分发的衍生作品都必须开源。**不能把它的代码抄进一个闭源或未定许可证的产品。**

**我们该抄的 3 件事**

1. **实体清单当检查表用**（不是抄代码）。把 TREK 的 166 个实体当成"旅行领域到底涉及什么"的清单，挑出我们缺的 7 个（§2.5），其余明确写"不做"。
2. **addon 式功能开关**。我们的 `Trip` 已经有 `transportMode`、`mustVisit` 这类开关，但没有"功能级开关"。加一个 `features` 配置，让"费用/文档/协作"可以按用户或按旅行开启，避免功能堆叠压垮主路径。
3. **迁移前快照 + schema 基线**。我们的 `store.js` 有 revision 和事务，但没有"迁移前自动快照 + 可回滚到迁移前"的能力。这是 P4 引入 Reservation/Document 前的必备。

**不该抄的**

- 插件市场（没有第三方生态，做了就是自娱）
- 实时协作 WebSocket（见 §6.4 否决清单）
- 多数据库方言支持（我们只有 SQLite）

### 3.3 FloatTrip：把"LLM 规划"做成了工程

**它最值得学的一点：LLM 只负责语义，排程必须确定性。**

```text
app/planning/
  candidate_builder.py   ← 从「权威 POI 索引」里组装候选池
  optimizer.py           ← OR-Tools CP-SAT 求解（DAY_START=9:00, DAY_END=21:00,
                            TRANSFER_MIN=20, LUNCH_WINDOW, DINNER_WINDOW）
  scoring.py             ← ScoringProfile + evaluate_itinerary + QualityViolation
  nodes.py               ← LangGraph 节点；违规抛 PlanningQualityError
  reliability.py         ← 可靠性/降级
app/runtime/models.py    ← Run 状态机：queued/running/waiting_user/succeeded/failed/cancelled
                            + DisconnectPolicy.CONTINUE/CANCEL
```

三个可以直接搬的概念：

1. **Authoritative candidate pool（权威候选池）**：LLM 提出"想去哪"，但候选池只能来自 `authoritative_poi_index()`——LLM 不能凭空造点。**这正是我们 `points.json` 的角色，但我们还没把它用在 AI 规划上。**
2. **Quality Gate 抛异常而不是返回坏结果**：`PlanningQualityError` 一旦触发就整轮失败并可重试。对比我们的 `evaluateDay()`——它返回 `structural: infeasible` 但**不会阻止生成**。生成器仍然会产出一份不可行的计划，只是标红。
3. **Run 状态机 + 断线策略**：AI 规划是长任务，用户关页面后是继续还是取消，必须显式定义。我们的 AI 规划是同步请求，超时即失败，无恢复。

**它的局限**

- 只用高德（中国境内），对我们无参考价值。
- CP-SAT 在我们的数据量下是杀鸡用牛刀：8 个点位的排列组合，插入式局部搜索（我们已有的 `solver.js`）足够。
- **无 LICENSE = 保留所有权利。** 一行代码都不能抄。

**对 v5 的启示：** 我们的 `engine.js` + `feasibility.js` 已经比 FloatTrip 更适合"可信"这个方向（它没有证据模型，没有 unknown 语义，没有开放日历的周表/例外）。**不要在求解器上追赶，要在证据上领先。**

### 3.4 Travel-Plan-Page：契约驱动的范本

**它的核心资产不是代码，是 `references/` 里的规范：**

```text
schemas/
  travel-data.schema.json    (15KB)  ← 目的地事实
  trip-data.schema.json      (11KB)  ← 行程
  trip-config.schema.json    (2KB)   ← 配置
  source-facts.schema.json   (12KB)  ← 事实来源
  core-integrity.schema.json (0.9KB) ← 完整性约束
references/
  golden-contract.md / golden-map-spec.md / golden-ui-spec.md
  golden-ledger-spec.md / golden-behavior-spec.md
  data-duplication-matrix.md  ← 「一个事实只能有一个家」
  data-migration-map.md / stable-id-proposal.md
  known-issues.md
```

**三个可以直接借的：**

1. **`travel-data` 与 `trip-data` 分离**：事实（点位、开放时间、票价）和行程（谁在哪天去哪）是两种生命周期完全不同的数据。我们的 `points.json` 和 `Trip` 已经分开了，但没有**契约层的强制约束**——`points.json` 的字段是 `check-data.mjs` 手写的规则，不是 schema。
2. **`source-facts` schema**：每条事实带 `value / source / collectedAt / reviewAfter / status`。这正是我们 `sources[]` 想做但没做全的。可以直接抄 schema 结构，MIT 允许。
3. **`data-duplication-matrix.md`**：明确"哪个字段在哪些文件里出现、谁是权威"。我们的 `routes.json` 里 `point`（展示快照）和 `pointId`（权威引用）就是这个问题的解法，但没有文档化，新人会误改快照。

**它的局限**

- 只有 3 个测试文件，工程质量远低于我们。
- 产品形态是"生成一个静态页面"，没有执行、没有协作、没有数据回流。**它是"输出物"，我们是"系统"。**

### 3.5 travel-agent：权限与代管边界是产品设计

**它最成熟的地方是"知道自己不该做什么"。**

- 浏览器 Agent 走到支付页**主动停下**，把控制权交回用户。
- `docs/decisions/` 下是按日期命名的小决策记录（`2026-08-26-trip-as-server-entity-owning-a-directory.md`、`2026-08-31-cap-agent-tasks-at-200-turns.md`），每条只讲一个决定和理由。**这是单人/小团队最该学的文档习惯。**
- `docs/research/competitors.md` 和 `mindtrip.md` 是我见过的最诚实的竞品调研之一：明确标注"Skift 403，结论来自搜索摘要"。

**它的架构**

```text
packages/
  browser-cli / browser-extension / core / desktop / server / skills / web
```

Electron 桌面端 + 浏览器扩展 + 本地 server + skills 市场雏形。**"trip as a folder"**——一次旅行对应磁盘上一个目录，里面有行程、截图、票据、笔记。这个心智模型非常强，比"数据库里的一行记录"更贴近用户。

**不能抄的**

- 浏览器自动化代订（行业成功率 <50%）
- Electron 打包（我们做 PWA 更轻）

**该抄的：**

1. **决策记录（ADR）习惯**。我们有一份 601 行的 `ROADMAP.md`，但没有"为什么当初不做 X"的记录。半年后没人记得为什么拒绝 CP-SAT。
2. **"止步于支付"的产品诚实**。对应我们：明确写"不代订、不代付、不做签证代办"，把 AI 的能力边界写在 UI 上。
3. **trip-as-folder 的导出心智**：我们的离线包应该导出一个**目录结构**（`trip.json` / `day-1.md` / `tickets/` / `photos/`），而不是一堆散文件。

### 3.6 personalized-travel-guide-skill：内容生产流水线

**它的核心是一句原则：**

> "The public template is an empty component scaffold, never evidence for a destination."
> （公开模板只是空组件脚手架，永远不能作为目的地的证据。）

这句话和我们 `unknown` 的纪律完全同源：**空壳不是事实**。

**它的结构**

- `assets/intake-questionnaire/` —— 结构化问卷，而不是一个空白聊天框。用户回答 12 个问题（同行人、预算、体力、兴趣、忌口、拍照偏好……），比"你想去哪"有效 10 倍。
- 8 模块手册 IA（行前 / 交通 / 住宿 / 每日 / 餐饮 / 应急 / 文化 / 预算）
- `scripts/` 138 个脚本组成的 research → QA → publish 管线
- 可选 Cloudflare 共享部署

**该抄的：**

1. **Intake Questionnaire**。我们的生成页现在是一堆表单字段（城市、天数、兴趣）。改成**一次 12 题的引导式问卷**，转化率和结果质量都会提升。
2. **8 模块手册作为内容 IA**。我们的笔记页没有结构。照这个 IA 给每个城市生成一份"城市手册"，比散落的点位强得多。
3. **模板 ≠ 证据** 的纪律，写进 `AGENTS.md`。

### 3.7 ticket-monitoring：证据与节流的工程范本

**它解决的是"信息会变"这个问题。**

```text
core/
  channels.py / channel_alert.py / channel_links.py  ← 多渠道抽象
  pacing.py        ← 请求节流
  login_slots.py   ← 登录态管理
  health.py / health_diag.py  ← 自诊断
  flighthist.py / flightnorm.py  ← 历史与归一化
  alerter.py / notifier.py / radar_alerts.py  ← 告警去重与分发
  702 个测试
```

**该抄的：**

1. **告警去重 + 节流**。我们要做"事实过期提醒"（开放时间变了、票价涨了），必须有一样的纪律，否则用户会被淹。
2. **`health_diag` 自诊断**。我们的 `tools/` 有质量门，但没有"运行时健康"——比如"这个城市 30 天没复核过"。加一个 `data-health.json` 端点。
3. **历史版本**。`flighthist` 保存价格历史。我们的 `FactRevision` 应该保存"开放时间的历史值"，这样能回答"它去年周一开吗"。

**不能抄的：**

- 五渠道爬虫（ToS 风险 + 维护成本）。我们只做**人工/半自动 + 官方页面快照**。

- **这正是 v5 的资源配置依据：守住左侧的三列优势，补右侧的四列短板，但每一列只做到"够用"，不追求 TREK 的完备度。**

### 3.9 许可证红线（商业化前必须理清）

| 仓库 | 许可证 | 能做什么 | 不能做什么 |
|---|---|---|---|
| TREK | AGPL-3.0 | 学习架构、读实体清单、参考交互 | 复制代码到闭源产品；复制后整体必须 AGPL 开源（含网络服务） |

> **本仓库目前没有 LICENSE 文件**（`git remote` 为 `silveryunna/russia-map`，公开仓库无许可证 = 默认保留所有权利）。这带来两个问题：

## 4. 市场与竞争格局

### 4.1 三个硬事实（决定了我们不该做什么）

**事实一：AI 助手带来的预订量约等于零。**

Booking Holdings 2026 Q2 财报电话会，CFO Ewout Steenbergen 回答分析师提问时说：来自大语言模型的流量（付费 + 非付费合计）"**显著低于我们间夜量的 1%**"，且"**过去几个月、几个季度没有实质变化**"。同期 Booking Holdings 单季间夜 **3.25 亿**，同比 +5%。

> 换算：全球所有 AI 助手加起来，一个季度带来不到 300 万间夜——比 Booking 正常增长一年新增的 1,600 万间夜还少。
> 来源：[Hospitality.today, 2026-08-10](https://www.hospitality.today/article/booking-com-just-told-investors-how-little-ai-actually-books) · [PhocusWire](https://www.phocuswire.com/news/finance/booking-holdings-q2-2026-earnings)

**事实二：OpenAI 自己撤回了对话内结账。**

2026-03，The Information 报道并经 OpenAI 发言人向 Skift 确认：ChatGPT 的购物策略转向"**发现与研究**"，把结账留给第三方开发者，Agentic Commerce Protocol 只作为连接基础设施。

> 来源：[Skift, 2026-03-05 "ChatGPT Bails on Transactions"](https://skift.com/2026/03/05/openai-chatgpt-checkout-walkback/)
> 原文措辞："OpenAI built the checkout tech but couldn't get users to actually buy."

**事实三：浏览器 Agent 代订在真实任务上不可靠。**

行业实测普遍 <50% 成功率，遇 CAPTCHA 直接放弃。OpenAI 2025-08 关停 Operator、2026-08 移除 Agent mode；Google Chrome auto browse 刻意在 "Place Order" 前刹车。

**三条事实合起来推出一个结论：**

```text
规划  →  已被商品化（边际成本趋零）
交易  →  闭环还早（<1%，且平台自己在退）
中间  →  无人认真做（可信事实 / 离线执行 / 同行对齐 / 记忆）
```

**我们要站的位置，就是那个"中间"。**

### 4.6 竞争空位与我们的位置

**空位定义：**

> 一个中国旅行者，去莫斯科/阿拉木图，出发前 3 天想知道"周三到底哪些馆开、地铁怎么坐、要不要预约"，到当地没网时想知道"现在该去哪、下一站在哪、晚了 40 分钟怎么办"，回来想知道"这趟到底花了多少、值不值"。
>
> **今天没有一个产品完整回答这三段。**

**我们的位置（一句话）：**

> **俄罗斯/中亚 中文旅行者的「行前核验 + 行中执行 + 行后复用」作业系统。**
> 不生成最漂亮的行程，生成**最不会出错**的行程。

**这个定位的三个必然推论：**

1. **必须深度优先。** 一个城市做到 90 分，胜过九个城市做到 40 分。
2. **必须离线优先。** 现场没有网络是常态，不是异常。
3. **必须可分享。** 一个人的行程只有变成"能给别人的东西"，才有传播。

### 5.2 逐一展开（前六项）

#### B1 数据的广度幻觉 —— 最致命

**证据：** §2.3 的表。开放时间覆盖率 2.7%，可信点位 6.1%，实测停留 0%。

**为什么致命：** 整个 v4/v5 的差异化叙事是"可信"。如果用户打开莫斯科之外的任何一个城市，看到的都是"开放时间：未知"，那"可信"就变成了"什么都没说"。**用户不会因为你说"我不知道"而感谢你，只会觉得这个产品没用。**

**根因：** 把"点位数量"当成了进度指标。`check-city-duration.mjs` 只校验"有没有停留时长"，不校验"开放时间是否已知"——因为一旦校验，莫斯科就过不了。

**修法：**
1. **换指标**：从"点位总数"改为"**决策就绪点位数**"（有坐标 + 停留 + 开放日历 + 官方来源 + 未过期）。
2. **换门槛**：`check-city-duration` 增加 `--require-hours` 模式，对**样板城市**强制开放时间覆盖率 ≥70%。
3. **换范围**：莫斯科从 38 → 60 个"高频点位"，其余显式标注"资料待补"，不假装可用。
4. **换叙事**：首页统计从"626 个点位"改为"60 个已核验点位 · 12 个已核验动线"。

#### B2 没有真实用户回路 —— 同样致命

**证据：** 全站 0 处 analytics / beacon；0 处 `navigator.share`；`smoke-test.mjs` 只验证渲染，不验证使用；M1 现场验收至今未做。

**为什么致命：** 项目所有重大决策（要不要 CP-SAT、要不要协作、要不要费用）都建立在**站长的直觉**上。n=1 的样本会系统性高估"有经验的旅行者"的需求，低估"第一次出国的人"的困惑。

**修法：**
1. **埋点最小集**（§10.3）：`page_view` / `trip_generated` / `capsule_downloaded` / `share_viewed` / `item_completed` / `verification_done`。本地缓冲、批量上报、可关闭、不含 PII。
2. **3 人现场测试**：站长 + 2 位真实用户（一位有经验、一位第一次去俄罗斯），全程录屏 + 事后访谈。
3. **把"没有现场数据"写进路线图的门禁**：没有 3 人数据，不进入 P4。

#### B3 内容层空转

**证据：** `photos/index.json = []`；`content/notes/` 只有 `example.md`。

**为什么严重：**  
- 产品名「旅行笔记」承诺的是**记忆**，交付的是**排程**。  
- 相册/笔记是留存的关键（用户回来才会打开），而现在这两个页面是空的。  
- 空页面比没有页面更伤：用户点进去，看到空白，会认为"这产品还没做完"。

**修法（二选一，不能拖）：**
- **选项 A（推荐）**：把相册/笔记从主导航隐藏，首页只留地图/清单/行程/今天四个入口，等有内容再放出来。
- **选项 B**：用站长自己的莫斯科行先填 20 张照片 + 3 篇笔记，作为"样板内容"。

> 我更倾向 A：先诚实，再丰富。一个只有 4 个入口但每个都能用的产品，好过 10 个入口 6 个是空的。

#### B4 分发为零

**证据：** `sitemap.xml` 5 条 URL；0 个 OG 标签；0 个预渲染；626 点位 0 个独立页面。

**为什么严重：** 数据护城河的前提是**数据能被发现**。现在的架构让 3 个月的积累在搜索引擎和 AI 爬虫眼里等于不存在。而 SEO 是单人项目唯一负担得起的获客渠道。

**修法：**
1. **构建期预渲染**（Vite 插件或独立脚本）：为每个城市生成 `/city/moscow.html`，为 Top 100 点位生成 `/place/p001.html`，内含 JSON-LD `TouristAttraction`。
2. **sitemap 从数据生成**，不再手写。
3. **OG 图构建期生成**（SVG 模板 → PNG），每页一张。
4. **每个城市页有 800 字以上的可读内容**（不是纯列表），否则会被判为低质。

#### B5 时间模型

**证据：** §2.6。`today.js:17-19` 读设备时间；`execution.js:135` 用 `toISOString()` 取 UTC 日期；`Day` 要求 `endTime > startTime`；`feasibility.js` 0 处引用 `timeZone`。

**为什么严重：** 这不是"体验问题"，是**正确性问题**。一个人在北京时间凌晨 1 点给莫斯科的行程点"完成"，Visit 的日期会落到前一天，导致"计划—实际"对比永久错位。而一旦接入航班/火车（绝对时刻 + 时区），整个模型要重写。

**修法：**
```js
// 1) Trip 增加时区与货币
Trip.timeZone = 'Europe/Moscow'   // 默认取首城
Trip.currency = 'RUB'

// 2) Day 窗口改为「起点 + 时长 + 跨日偏移」
Day.window = { start: '09:00', minutes: 720, endDayOffset: 0 }  // 兼容旧 endTime

// 3) 时刻统一为 TimeAnchor
TimeAnchor = { instantUtc: '2026-11-09T06:00:00Z', local: '09:00', tz: 'Europe/Moscow', precision: 'exact' }

// 4) Today 用 trip 时区判定"今天"
const todayInTrip = () => formatInZone(new Date(), trip.timeZone)  // Intl.DateTimeFormat
```

#### B6 领域模型缺 7 实体

**证据：** §2.5。

**为什么严重：** "完整旅程"不是加页面能解决的，是**模型里没有位置**。`type:'reservation'` 只是一个带 60 分钟时长的块——它甚至不能存确认号。用户想把机票信息放进去，只能写进 `note` 字段，然后永远无法被结构化使用（提醒、导出、核对）。

**修法：** 按依赖顺序引入，不要一次全上：
```text
P3: Share（公开只读快照）+ RouteTemplate + FactRevision
P4: Reservation（含 Document 引用）+ Document + Member + Expense
```

### 5.3 后六项（简版）

- **B7 单人产能**：v5 的 26 周主干 ≈ 260–390 小时，加上内容运营 200+ 小时，已经逼近 10–15h/周 × 52 周的上限。**必须做减法**（§8.5），否则一定烂尾。
- **B8 验证系统自欺**：修法见 §2.7，1 天工作量，**本周就该做**。
- **B9 前端单文件**：`plan.js` 1,186 行已经无法被单人在一个上下文里理解。拆成 5 个 <250 行的控制器（§7.8）。不必上 TypeScript，但关键纯函数要加 JSDoc typedef。
- **B10 移动端未验证**：`smoke-test.mjs` 的 `probePlan()` 只有桌面。加一个 390×844 的 plan + today 冒烟，成本 30 分钟。
- **B11 无商业模式**：不是现在的优先级，但要在 90 天内**卖出第一单**（§11），否则永远不知道值多少钱。
- **B12 许可证空白**：P0 决策，见 §3.9。

### 5.4 共同根因

```text
所有盲点指向同一个东西：

    产品没有"用户"，只有"使用者假设"。

工程上，每一个决定都在回答"系统是否正确"；
产品上，没有一个决定在回答"谁会在什么时刻因为什么而感激它"。
```

**这不是能力问题，是注意力分配问题。** 好消息是：注意力可以立刻改，而且不需要重写任何代码。

### 6.3 旗舰 A：证据链编译器（Trip Compiler with Proof Chain）

#### 用户故事

> 小林，28 岁，上海，第一次去俄罗斯，出发前 3 天。
> 她打开行程，看到 Day 2 顶部写着：
>
> **「这天结构上可排。但 6 件事还没确认，其中 2 件会直接让你白跑一趟。」**
>
> 点开，是一张按影响排序的清单：
>
> | 影响 | 事项 | 现状 | 怎么确认 | 截止 |
> |---|---|---|---|---|
> | 🔴 高 | 特列季亚科夫画廊 周一闭馆？ | 资料 2024-06，已过期 | 官网 / +7 495 xxx | 出发前 1 天 |
> | 🔴 高 | 克里姆林宫 军械库需单独预约 | 未知 | 官网预约页 | 出发前 3 天 |
> | 🟡 中 | 古姆百货 营业至 22:00？ | 第三方，未核 | 地图 App | 到当天 |
> | 🟡 中 | 地铁 5 号线 环线是否检修 | 未知 | 莫斯科地铁官网 | 出发前 1 天 |
> | 🟢 低 | 餐厅是否需要订位 | 未知 | 电话 | 当天 |
> | 🟢 低 | 门票价格 | 2025 年数据 | 官网 | 无 |
>
> 她点"已确认"，选择"周一闭馆"，系统把 Day 2 的特列季亚科夫**自动挪到 Day 3**，并提示"Day 3 会晚 40 分钟收工，接受吗？"

#### 产品形态

```text
┌─ 行程页 · Day 2 ────────────────────────────────────┐
│ 结构：可排 ✅   证据：条件式 ⚠️                        │
│ ┌──────────┬──────────┬──────────┬──────────┐       │
│ │ 已核实 12 │ 估算 8   │ 待核 6   │ 过期 2   │       │
│ └──────────┴──────────┴──────────┴──────────┘       │
│ 最大风险：2 项可能导致「到了才发现关门」（−180 分钟）    │
│ [查看核验清单 →]  [导出为行前任务 →]                   │
└─────────────────────────────────────────────────────┘
```

**三道界面：**

1. **可信度带**（不是分数，是四个计数 + 一句人话结论）
2. **核验清单**（按 `impactMinutes` 排序，每条可"标记已确认 / 无法确认 / 不重要"）
3. **一键应用**（确认结果直接改 fact，触发重排/Plan B/提示）

#### 数据模型

```js
// 每条结论都是一个 Claim，不是一个布尔值
Claim = {
  id, tripId, dayId, itemId,
  field: 'openHours' | 'ticket' | 'duration' | 'transit' | 'reservation',
  status: 'verified' | 'third-party' | 'estimated' | 'unknown' | 'stale' | 'conflict',
  value,                       // 结构化值
  source: { type, url, title, collectedAt, reviewAfter },
  impactMinutes,               // 这条错了，当天最多损失多少分钟
  verifyBefore: '2026-11-06',  // 出发前多久必须确认
  verifiedBy: 'user' | 'editor' | 'official',
  verifiedAt,
}
```

**关键设计：`impactMinutes` 是整个功能的灵魂。** 它把"未知"翻译成"你会损失多少时间"，用户才知道先确认哪个。

#### 技术方案

```text
src/pages/plan/evidence.js        // 纯函数：claim 生成、影响估算、排序
src/pages/plan/evidence-ui.js     // 可信度带 + 清单渲染
src/pages/plan/verify.js          // 核验动作 → FactRevision → 重排
tools/evidence-coverage.mjs       // CLI：按城市/动线报告覆盖率与过期项
data/facts/{city}.json            // 结构化事实（与 points.json 分离，按字段粒度）
```

**为什么事实要独立成 `data/facts/`：** `points.json` 现在是"点位属性大杂烩"，一个点位 20+ 字段。事实需要独立的生命周期（采集/复核/过期/冲突），混在点位里无法做 TTL 扫描。

#### 验收标准

| 指标 | 目标 |
|---|---|
| 莫斯科 D1–D4 + 3 条专题线，每条 claim 都有 status | 100% |
| 莫斯科 Top 60 点位开放时间已知 | ≥ 90%（其中 Top 40 必须 100%） |
| 核验清单条目有 `impactMinutes` 与 `verifyBefore` | 100% |
| 用户完成核验清单后，行程自动重排且不产生新硬冲突 | 100% |
| 3 位真实用户中，至少 2 位在出发前完成 ≥5 项核验 | ≥ 66% |
| 真实旅行中"到了才发现闭馆/没票"事故 | **0 次** |

#### 为什么是护城河

- **它是劳动密集，不是资本密集。** 竞品可以用一周做出同样的 UI，但做不出"2026 年 11 月特列季亚科夫周一闭馆"这条数据。
- **它随使用变强。** 每次用户确认/纠正，都是一次数据回流（FactRevision），别人抄不走。
- **它定义了品类语言。** "条件式可排""影响 180 分钟""出发前 6 项待核"——这些词一旦被用户接受，后来者只能跟着说。

#### 失败模式

| 失败 | 信号 | 应对 |
|---|---|---|
| 用户不想看清单 | 打开率 <20% | 收敛到"只看 Top 3"，其余折叠 |
| 核验成本太高 | 完成率 <30% | 提供"帮我打电话/发邮件"的半自动草稿 |
| 数据补不完 | 60 点耗时 >8 周 | 缩到 30 点，先跑通闭环 |

### 6.4 旗舰 B：离线胶囊 + Today 2.0 + 行前压力测试

#### 用户故事

> 老周，35 岁，带老婆和 6 岁女儿去莫斯科 5 天。出发前一晚，他在家用 Wi-Fi 点了一下"生成胶囊"，得到一个 **2.3 MB 的单文件 `moscow-trip.html`**，发到家庭微信群。
> 老婆在机场用手机打开，不用装 App、不用登录，看到的是：今天去哪、几点、怎么走、厕所在哪、孩子累了可以砍哪一站。
> 到了第三天，地铁延误 50 分钟。老周点"我晚了 50 分钟"，页面当场把下午三项重排，砍掉一个可选项，保留女儿的动物园，并提示"这样会晚 20 分钟吃饭，附近有 3 家备选"。
> 全程飞行模式。

#### 三个组件

**B-1 单文件离线胶囊（Capsule）**

```text
moscow-trip.html   ← 自包含：HTML + CSS + JS + 数据 + 内联 SVG 地图
  ├─ trip.json     （内嵌）
  ├─ day-1..5      （可读文本 + 时间轴）
  ├─ tickets/      （base64 缩略图，可选）
  ├─ emergency.md  （急救/使馆/报警/医院）
  └─ version: { sha, builtAt, expiresAt, sourceTripRevision }
```

技术要求：
- **零外部请求**（含字体、图标、地图瓦片）——地图用构建期生成的 SVG 简化图 + GPX 外跳
- **单文件 < 5 MB**（微信可发）
- **打开即用**，无 Service Worker 依赖
- 带 `expiresAt`，过期后顶部红条提示"资料快照 2026-11-01，已 14 天未复核"

**B-2 Today 2.0 作战面板**

现在的 `today.html` 是"当前/下一项 + 完成/跳过"，是**记录工具**。2.0 要做成**决策工具**：

| 模块 | 现在 | 2.0 |
|---|---|---|
| 缓冲 | 只显示"下一项到场 − 路上 − 现在" | 倒计时 + **颜色分级**（绿 >20min / 黄 5–20 / 红 <5） |
| 延误 | 无 | **"我晚了 N 分钟"** 一键重排（复用 `solver.js` + `repair.js`） |
| 替代 | 需手动开 Plan B | 当前项旁边常驻 **"不想去了，换这个"**（预计算 2 个候选） |
| 同伴 | 无 | 只读链接：谁在哪、谁完成了什么（可选，默认关） |
| 离线变更 | 直接写 IndexedDB | 变更进 **outbox**，恢复网络后合并，冲突可见 |

**B-3 行前压力测试（Pre-mortem）**

```text
输入：一份 Trip
模拟 5 个场景：
  1. 某个必去点临时闭馆
  2. 上一站延误 45 分钟
  3. 下雨（户外项不可用）
  4. 体力只剩 60%（砍掉步行 >1.5km 的项）
  5. 打车预算翻倍（不能全程打车）
输出：每个场景一张「如果 X，就 Y」卡，离线可查
```

技术上完全复用现有 `feasibility.js` + `repair.js` + `alternatives.js`——**几乎不需要新引擎，只需要新的编排与呈现**。这是投入产出比最高的一项。

#### 验收标准

| 指标 | 目标 |
|---|---|
| 飞行模式下完成：看今天 / 打卡 / 看核验清单 / 看应急卡 | 100% |
| 单文件胶囊体积 | < 5 MB |
| 胶囊在 iOS Safari / Android Chrome / 微信内置浏览器打开 | 3/3 通过 |
| 延误 45 分钟一键重排后产生新硬冲突 | 0 |
| 非站长用户独立用胶囊完成一天，无需提问 | ≥ 2 人 |
| 5 个压力场景都能输出可执行卡片 | 5/5 |

#### 为什么是护城河

- **它是"最后一公里"，而所有竞品都在"第一公里"。** OTA 管预订，AI 管生成，没人管"你站在红场，手机没网，老婆孩子饿了"。
- **它的成本被现有引擎摊薄了。** 别人要做需要重建一套可行性引擎；我们已经有了。
- **它天然产生口碑。** "这个文件发群里就能用"是最容易传播的产品形态。

#### 失败模式

| 失败 | 信号 | 应对 |
|---|---|---|
| 胶囊太大发不出去 | >10 MB | 图片降级为占位符 + 外链 |
| 微信内置浏览器限制 | 打不开 | 降级为纯 HTML + 内联 CSS，去掉 JS 交互 |
| 用户不用 Today | 打开率 <30% | 说明入口太深，做成 PWA 快捷方式 / 锁屏卡片 |
| 重排结果不如手动 | 用户改回去 >50% | 只提供 2 个候选，不做全自动 |

### 6.5 旗舰 C：Guest-first 协作 + 亲证路线图 + MCP 分发

#### 用户故事

> **协作**：小陈做了 7 天中亚行程，发给 3 个朋友一个链接。朋友不用注册，输入昵称就能：看到完整行程、给 3 个候选餐厅投票、认领"订阿拉木图酒店"这个任务、在某个点上留言"这里我想多待 1 小时"。
> **亲证**：小陈走完后，系统记录"阿拉木图 Green Bazaar → 升天大教堂，步行 18 分钟（我们走过 3 次，中位 18，最长 24）"。下次别人排这段，用的是这个数，不是模型估算。
> **分发**：朋友在 ChatGPT 里问"阿拉木图 3 天怎么玩"，ChatGPT 通过 MCP 调用我们的 `list_route_templates('阿拉木图')`，返回小陈那条线，并附上"数据来自 xxx，最后核验 2026-10"。

#### C-1 Guest-first 协作

**核心设计：没有"注册"这个动作。**

```text
分享链接 → https://julyyunna.art/s/abc123
  → 输入昵称（或微信昵称）→ 得到一个 guestToken（存 localStorage）
  → 能力：只读行程 / 投票 / 认领任务 / 留言 / 上传照片
  → 不能：改时间、删点位、看费用明细（除非 owner 授权）
```

数据模型：

```js
Member = {
  id, tripId, role: 'owner'|'editor'|'guest',
  displayName, guestTokenHash, joinedAt, lastSeenAt,
  capabilities: ['view','vote','claim','comment'],
}
```

**为什么不做实时协同编辑：** 成本（CRDT/OT + WebSocket + 冲突 UI）远超收益。真实场景里，同行者 90% 的需求是"看"和"表态"，不是"同时改"。

#### C-2 亲证路线图（Witnessed Route Graph）

**这是全项目最有想象空间的一项。**

```js
WitnessedLeg = {
  fromId, toId, mode,
  samples: [{ minutes, at, tripId, memberId }],
  medianMinutes, p90Minutes, sampleCount,
  firstRecordedAt, lastRecordedAt,
  confidence: 'low' | 'medium' | 'high',   // 由 sampleCount + 方差决定
}
```

规则：
- **至少 3 个样本**才展示"我们走过 N 次"
- **收缩估计**：`adjusted = (n * median + k * prior) / (n + k)`，k=3，prior 用矩阵/估算值
- **永远与第三方路线并列显示**，不合并成一个数
- 用户可查看/撤销自己的样本

**为什么别人抄不走：** 这需要真实用户真实走完真实路段。TREK 有用户但没有中文长尾目的地；Wanderlog 有用户但不做现场记录；TripIt 只记航班。**这是唯一一个"用户越多、数据越准、体验越好"的飞轮。**

#### C-3 MCP Server（分发面）

2026 年的新渠道：让 AI 助手调用我们。

```text
tools:
  search_places(city, query, type?)         → 点位 + 开放时间状态
  get_opening_hours(placeId, date)          → 结构化 + 来源 + 复核日期
  compile_trip(city, days, interests, pace) → Trip（含证据状态）
  list_route_templates(city)                → 创作者路书
  get_transit_leg(fromId, toId, mode)       → 亲证/第三方/估算三档
```

**关键：每个返回都带 `source` 与 `lastVerified`。** 让 AI 在回答里自然带出"（数据来自 xxx，2026-10 核验）"——这就是最好的品牌曝光。

技术上：`api/mcp.php` 或一个独立的 Node 小服务，复用现有 JSON 数据。**不需要重写后端。**

#### 验收标准

| 指标 | 目标 |
|---|---|
| guest 从点开链接到看到行程 | ≤ 10 秒，0 次跳转 |
| guest 加入转化率（打开→输入昵称） | ≥ 40% |
| 亲证路段样本数（3 个月内） | ≥ 50 条 |
| 有亲证数据的路段，估算误差中位数 | 下降 ≥ 30% |
| MCP 被至少 1 个外部 AI 客户端调用 | 1 个 |
| MCP 返回带来源的比例 | 100% |

#### 失败模式

| 失败 | 信号 | 应对 |
|---|---|---|
| 没人分享 | 分享按钮点击 <5% | 不是功能问题，是行程不够好——回旗舰 A |
| guest 只看不改 | 投票参与 <10% | 降低门槛：不用输昵称，匿名也能投 |
| 亲证样本太少 | 3 个月 <20 条 | 先只在站长自己的行程里积累，作为"内部数据" |
| MCP 没人用 | 0 调用 | 转向：先做 SEO，MCP 是期权不是主线 |

### 6.6 明确否决的功能（以及为什么）

| 功能 | 否决理由 |
|---|---|
| **实时多人协同编辑** | CRDT/OT + 冲突 UI + WebSocket，成本 > 3 个月；真实需求 <10%。用"异步 + 投票 + 认领"覆盖 90%。 |
| **自动订票 / 代付** | 行业 <1%，平台自己在退；合规与信任成本极高。只做"一键跳转官方页 + 提醒"。 |
| **通用浏览器 Agent** | 实测 <50%，CAPTCHA 即死。不做。 |
| **全城交通矩阵爬取** | 2GIS 配额限制（约 50 次/天），扩面必然 429。改为"按需 + 亲证"。 |
| **自建全球 POI 库** | OSM/Wikidata 已经足够，我们的价值在"核验过的事实"，不在"点位坐标"。 |
| **社交 Feed / 关注关系** | 没有用户基数做社交等于许愿。 |
| **AI 聊天式规划首页** | 已被商品化，且会让产品变成"又一个 ChatGPT 壳"。规划入口保留表单 + 问卷。 |
| **CP-SAT / 重型求解器** | 8 个点位的组合，插入式局部搜索足够。引入只会增加不可解释性。 |
| **多语言（英/俄）** | P6 之后再评估。中文深度是我们的起点优势，过早国际化会稀释。 |
| **小程序 / 原生 App** | PWA + 单文件胶囊已经覆盖"不装 App"的场景。原生是重资产。 |

## 7. 平台架构蓝图

### 7.1 分层与依赖规则

```text
┌───────────────────────────────────────────────────────────┐
│ L4 分发面   SEO 城市页 / 点位页 / 分享页 / MCP / RSS       │
├───────────────────────────────────────────────────────────┤
│ L3 界面     map  list  notes  album  plan  today  share    │
├───────────────────────────────────────────────────────────┤
│ L2 应用     compiler  execution  collaboration  content    │
├───────────────────────────────────────────────────────────┤
│ L1 领域     schema  feasibility  engine  solver  repair    │
│             evidence  time  money  offline                 │
│             （纯函数，零 DOM，零 storage，零 fetch）         │
├───────────────────────────────────────────────────────────┤
│ L0 适配     idb  api-client  telemetry  export  storage    │
└───────────────────────────────────────────────────────────┘
```

**三条硬规则（写进 `AGENTS.md`）：**

1. **L1 不得 import L0/L2/L3。** 纯函数层只能依赖彼此。现有 `feasibility.js`/`engine.js`/`solver.js` 已经做到了，新增 `evidence.js` 必须同样。
2. **L3 不得直接操作存储。** 页面只调 L2 的应用函数；L2 调 L0 的适配器。现在 `plan.js` 直接调 `store.saveTrip()`，属于可以保留的例外，但新页面不允许。
3. **每个新功能先回答"落在哪一层"。** 答不出来就是设计没想清楚。

### 7.2 领域模型 v3

在现有 Trip / Day / Item / Visit / ChangeEvent / TransitLeg 之上，补齐 7 个实体：

| 实体 | 作用 | 关键字段 | 引入阶段 |
|---|---|---|---|
| **Reservation** | 航班/火车/酒店/门票/餐厅的预订凭证 | `kind, provider, confirmationNo, startAt(TimeAnchor), endAt, cancellationDeadline, price{amount,currency}, documentIds[], status` | P4 |
| **Document** | 票据/证件/保险的引用（不存明文敏感信息） | `kind, filename, mime, size, sha256, storage('local'/'server'/'nas'), expiresAt, redactedFields[]` | P4 |
| **Share** | 一份不可变的公开快照 | `tripId, revision, token, visibility, redactions[], createdAt, expiresAt, viewCount` | P3 |
| **RouteTemplate** | 创作者的可复用路书 | `id, cityIds, days, authorId, license, version, forkOf, publishedAt` | P3 |
| **Member** | 行程参与者（含 guest） | `tripId, role, displayName, guestTokenHash, capabilities[], joinedAt` | P4 |
| **Expense** | 多币种费用与分摊 | `tripId, amountMinor, currency, fxRate, fxAt, payerId, shares[{memberId,weight}], category, receiptDocId` | P4 |
| **FactRevision** | 事实的修订历史 | `placeId, field, oldValue, newValue, status, source, evidenceUrl, collectedAt, reviewAfter, reviewerId` | P3 |

**v3 的核心变化不是"多了 7 张表"，而是三种数据分离：**

```text
事实（Fact）     ← 生命周期长、需复核、可冲突    → data/facts/ + FactRevision
计划（Plan）     ← 生命周期中、可编辑、有版本    → Trip/Day/Item
实际（Actual）   ← 生命周期长、不可篡改、可追加  → Visit/TransitLeg/Expense
```

现在这三者在 `points.json` + `Trip` + `Visit` 里**部分混在一起**（比如 `points.json` 的 `estimatedDuration` 既是事实也是默认值）。分离之后，"改事实"和"改计划"不再互相污染。

### 7.3 时间与货币模型

**时间三件套：**

```js
// 1) 绝对时刻：用于航班、火车、跨时区预订
TimeAnchor = {
  instantUtc: '2026-11-09T06:00:00.000Z',
  local: '09:00',
  tz: 'Europe/Moscow',
  precision: 'exact' | 'approximate' | 'date-only',
}

// 2) 当地窗口：用于一天的作息
DayWindow = {
  start: '09:00',
  minutes: 720,          // 12 小时
  endDayOffset: 0,       // 1 = 次日结束（跨午夜）
}

// 3) 行程时区：用于判定"今天"
Trip.timeZone = 'Europe/Moscow'   // 默认取首城；多城时每 Day 可覆盖
```

**向后兼容：** 旧数据 `endTime` 存在时，`normalizeTrip` 自动换算成 `DayWindow{ start, minutes: diff, endDayOffset: 0 }`。`endTime < startTime` 的旧数据（现在会被拒）按跨午夜处理，`endDayOffset = 1`。

**货币：**

```js
Money = { amountMinor: 125000, currency: 'RUB' }   // 最小单位，整数，避免浮点
FxRate = { from: 'RUB', to: 'CNY', rate: 0.078, at: '2026-11-01', source: 'cbr.ru' }
```

规则：**存储永远用原币种 + 最小单位；展示时才换算；汇率带时间戳，冻结在预订时刻，不用实时汇率回算历史账单。**

### 7.4 存储与同步：local-first 是宪法

```js
// P0–P2：只有本地
interface SyncAdapter {
  readonly kind: 'noop' | 'http'
  pull(since): Promise<ChangeSet>
  push(outbox): Promise<PushResult>
  subscribe(cb): Unsubscribe
}

class NoopAdapter implements SyncAdapter { /* 全部返回空 */ }
```

**为什么现在就要定接口：** 因为 P3 之后一旦有了 Share，P4 再有了 Member/Expense，数据就不再是"一个人的本地文件"。如果现在不定义 outbox 和 ChangeSet 的形状，将来同步会变成一次重写。

**Outbox 设计：**

```js
OutboxEntry = {
  id, entity: 'trip'|'visit'|'expense'|'member',
  entityId, op: 'create'|'update'|'delete',
  revision, payload, createdAt, attempts, lastError,
}
```

写入顺序永远是：**先写本地 → 再入 outbox → 再异步 push**。任何时候断网，本地都是完整的。

**冲突策略（复用现有 `saveTrip` 的乐观 revision）：**

| 场景 | 策略 |
|---|---|
| 同实体、远端 revision 更高 | 本地 rebase，失败则显式冲突 |
| 同 revision 不同内容 | 生成 `conflict` 记录，UI 展示"保留我的/用他的/合并" |
| 删除 vs 编辑 | 删除优先，编辑进"回收站"30 天 |

### 7.5 服务端演进：PHP 什么时候不够用

**现在够用。** `api/index.php` ~600 行，SQLite WAL，单机，覆盖登录/投稿/审核/AI 代理/Key 加密。这套东西的成本接近 0，**不要为了"架构先进"重写**。

**触发迁移的具体阈值（写死，避免拍脑袋）：**

| 信号 | 阈值 | 动作 |
|---|---|---|
| 单 Trip 并发写者 | > 5 | 加 WebSocket 或轮询 + 乐观锁（不是重写） |
| 日活 | > 10,000 | 引入 Redis 缓存 + 读写分离 |
| SQLite 写冲突 | 日均 `database is locked` > 100 次 | 迁移到 MySQL/PostgreSQL |
| 后台任务 | 需要定时抓取/推送 | 加一个独立 Node worker（不动 PHP） |
| 附件存储 | > 10 GB | 对象存储 + 签名 URL |

**迁移方式：** 永远"加一个服务"，不"重写一个服务"。PHP 继续做认证和投稿，新的 Node 服务只做它擅长的事（MCP、任务队列、SSG）。

### 7.6 内容流水线（从"补覆盖"到"补决策"）

现有管线（`tools/research-*.mjs`）已经很好：队列 → 候选 → 校验（verified 必须 official）→ 报告。缺的是**需求加权**和**回流**。

```text
┌──────────────┐
│ 需求信号      │  ← Trip 里被排入的点位、被查看的城市、
│ （demand）    │     分享页的浏览量、MCP 的查询词
└──────┬───────┘
       ▼
┌──────────────┐   权重 = 使用次数 × 影响分钟数 × 过期程度
│ 优先级队列    │
└──────┬───────┘
       ▼
┌──────────────┐
│ 候选采集      │  官方页面 / 电话 / 用户反馈 / 合作方
└──────┬───────┘
       ▼
┌──────────────┐
│ 校验          │  verified 必须 official；UGC 只能当线索
└──────┬───────┘
       ▼
┌──────────────┐
│ 人工复核看板  │  ← 新增：admin 里一屏看完"今天该核什么"
└──────┬───────┘
       ▼
┌──────────────┐
│ 发布 + TTL    │  每个字段独立 TTL（开放时间 90 天 / 票价 30 天 / 交通 180 天）
└──────┬───────┘
       ▼
┌──────────────┐
│ 现场回流      │  Visit / FactRevision / 用户"这里关门了"
└──────────────┘
```

**关键改动：**

1. **队列权重从"缺什么补什么"改为"用得多、影响大、快过期"优先。**
2. **新增 admin 复核看板**（现在只有 CLI）。
3. **字段级 TTL**，不是城市级。
4. **现场反馈直接进队列**，不需要人工转录。

### 7.7 可观测性与实验

**原则：第一方、最小、可关闭、不含 PII。**

```js
// src/shared/telemetry.js
const EVENTS = {
  page_view:        { page: 'map'|'list'|'plan'|'today'|'share' },
  trip_generated:   { city, days, engine: 'rule'|'ai', itemCount },
  trip_edited:      { op, count },
  capsule_exported: { format, bytes, days },
  share_created:    { visibility },
  share_viewed:     { referrer },
  guest_joined:     { role },
  item_completed:   { delayMinutes, source },
  verification_done:{ field, result: 'confirmed'|'denied'|'unknown' },
  mcp_called:       { tool },

```

- 本地存 IndexedDB，批量 30 秒或页面隐藏时上报
- 服务端只存聚合（日粒度 + 城市粒度），不存 IP、不存精确坐标
- 用户可在设置里一键关闭
- **不上 Google Analytics**（境外请求 + Cookie 合规 + 慢）

**实验：** 不做 A/B 框架（样本量不够）。用**前后对比 + 3 人访谈**代替。

### 7.8 `plan.js` 拆分方案

现状 1,186 行，混合了列表、创建、生成、编辑器、可行性行、条目面板、时间轴、Plan B、修复、AI、导入导出、撤销栈。目标：5 个文件，每个 < 250 行。

```text
src/pages/plan/

  list.js         ~150 行   行程列表、创建、复制、删除

  editor.js       ~240 行   天卡片、条目渲染、可行性行、时间轴挂载
  inspector.js    ~200 行   条目面板、停留 ±15、午餐/休息、Plan B、锁定
  io.js           ~120 行   导入导出、离线包、分享
  ai.js           ~100 行   AI 设置、模型选择、调用封装
  index.js         ~60 行   组装与路由
```

**拆分顺序（重要）：先搬纯渲染，后搬状态。**

1. 第 1 周：抽出 `io.js` 和 `ai.js`（依赖最少，风险最低）
2. 第 2 周：抽出 `list.js` 和 `generate.js`
3. 第 3 周：抽出 `inspector.js`
4. 第 4 周：抽出 `editor.js`，`index.js` 收口

**每步都必须跑 `npm test` + 冒烟 + 手动点一遍主路径。** 不要一次重写。

### 7.9 技术选型：明确"不改"的清单

| 项 | 决定 | 理由 |
|---|---|---|
| 框架 | **不引入 React/Vue** | 10 个页面的 MPA，原生模块 + 模板字符串足够；引入框架会让 9,000 行变成 20,000 行 |
| 语言 | **不上 TypeScript 编译**，但关键模块加 JSDoc | 纯函数层加 `@typedef` 就能获得 80% 的类型收益，零构建成本 |

| 地图 | **Leaflet + OSM/天地图** | 已稳定，换 MapLibre 无收益 |
| 存储 | **IndexedDB 为主**，localStorage 只做兼容投影 | 已落地 |
| 测试 | **node:test 风格的手写断言**，不引入 Jest/Vitest | 现有 19 个 `test-*.mjs` 运行快、零依赖 |
| 构建 | **Vite** | 已稳定 |
| 部署 | **push → cron pull** | 简单可靠；加一个 `/health` 端点和回滚脚本即可 |
| SSG | **新增一个构建期预渲染脚本**，不引入 Next/Astro | 只需要生成静态 HTML 片段，不值得引入框架 |

## 8. 路线图 v5

### 8.1 四条并行轨道

v4 是**串行阶段**（M0 → M1 → M2 → P3 → P4…），问题是任何一环延期都会让后面全部推迟，而且"分发"排到最后等于永远不做。

v5 改为**四条轨道并行**，每个阶段在四条轨道上各取一小步：

| 轨道 | 代号 | 关注 | 衡量的东西 |
|---|---|---|---|
| **信任** | T1 Trust | 事实、证据、时效、核验 | 决策就绪点位数、过期事实数 |
| **现场** | T2 Field | Today、离线、压力测试 | 飞行模式完成率、延误重排成功率 |
| **分发** | T3 Reach | SEO、分享、guest、MCP | 自然流量、分享打开率、guest 加入率 |
| **平台** | T4 Platform | 时间模型、实体、拆分、CI | 硬冲突数、构建时间、测试覆盖率 |

**任一阶段结束时，四条轨道都必须有交付物。** 不允许"这一阶段只做平台"。

### 8.2 阶段表

| 阶段 | 周期 | T1 信任 | T2 现场 | T3 分发 | T4 平台 | 退出条件 |
|---|---:|---|---|---|---|---|
| **P0 收口** | 2 周 | 建立 `data/facts/` schema | — | 埋点骨架 | CI parity、LICENSE、拆 `io/ai`、手机 smoke | 4 个漏跑门进 CI；`check-ci-parity` 上线；README 事实修正；LICENSE 落地 |
| **P1 莫斯科可信城** | 4 周 | **Top 40 点位 100% 开放时间/票价/来源**；覆盖率 CLI；证据链 UI v1（可信度带 + 清单） | Today 缓冲分级 | 城市页 SSG ×6 | `Trip.timeZone` + `DayWindow` | Top 40 覆盖率 100%；过期事实 = 0；跨午夜用例通过；6 个城市页可被索引 |
| **P2 现场闭环** | 4 周 | 证据链 v2（核验动作 → 自动重排 → FactRevision 预埋） | **Capsule v1** + Today 2.0 + Pre-mortem | 分享页（只读快照 + OG） | `evidence.js` 纯函数层 + 离线 outbox 骨架 | 飞行模式 100%；2 位非站长独立用胶囊完成一天；延误 45 分钟重排 0 硬冲突 |

| **P4 完整旅程** | 6 周 | 字段级 TTL 自动化 | 费用记录（离线） | 创作者主页 ×3 | `Reservation` + `Document` + `Member` + `Expense` | 一次真实旅行：预订导入 + ≥5 Visit + ≥3 笔费用 + 行后结算 |
| **P5 协作与回流** | 6 周 | 亲证路线图（≥50 段） | 同行者只读位置（可选） | **MCP Server** + 创作者 fork | 同步适配器（HTTP，可选） | 亲证段误差下降 ≥30%；MCP 被 1 个外部客户端调用 |
| **P6 分发放大** | 持续 | 第二城市（圣彼得堡）可信化 | — | ChatGPT App / 小红书内容矩阵 | 性能与可观测性 | 月自然流量 ≥5,000；第二城市 Top 30 覆盖率 ≥80% |
| **P7 商业化** | 触发式 | — | — | 定价页 + 支付 | 多租户（如需要） | 首单成交；或明确放弃商业化 |

**总工期：P0–P5 共 26 周（约 6 个月），P6 起常态化。**

### 8.3 依赖与关键路径

```text
P0 收口
 └─► P1 莫斯科可信城 ──► P2 现场闭环 ──► P4 完整旅程 ──► P5 协作回流
        │                    │                │
        └─► 城市页 SSG ──────┴─► P3 分享获客 ─┘
                                  │
                                  └─► P6 分发放大 ──► P7 商业化

关键路径 = P1 → P2 → P4 → P5
风险点   = P1（内容人力）与 P4（实体扩张）
```

**三条不能违反的顺序约束：**

1. **时间模型（P1）必须在 Reservation（P4）之前。** 否则预订实体会把错误的时间语义固化。
2. **证据链 UI（P2）必须在分享页（P2 末）之前。** 否则分享出去的是"没有可信度标注的行程"，会把"看起来可行"当成"可信"传播。
3. **guest 链接（P3）必须在 Member 实体（P4）之前。** 先用无账号方案验证需求，再决定要不要真正的成员体系。

### 8.4 资源核算：10–15 小时/周 到底能做什么

| 阶段 | 工程 | 内容/数据 | 合计 | 现实判断 |
|---|---:|---:|---:|---|
| P0 | 20h | 4h | 24h | ✅ 可行 |
| P1 | 30h | **30h** | 60h | ⚠️ 内容占一半，必须每天挤 30 分钟 |
| P2 | 45h | 10h | 55h | ⚠️ 最重的一段，Capsule 是硬骨头 |
| P3 | 40h | 15h | 55h | ✅ 可行 |
| P4 | 70h | 10h | 80h | ❌ 6 周 × 13h = 78h，**没有余量** |
| P5 | 60h | 15h | 75h | ❌ 同上 |

**结论：P0–P3（14 周，约 194 小时）是可信的；P4–P5 在原产能下必然延期。**

**三个选项：**

## 10. 指标、埋点与反指标

### 10.1 北极星指标

> **每周被真实执行的可信行程数（Verified Trips Executed, VTE）**

一份 Trip 计入 VTE，必须同时满足：

1. 本周内至少 **1 个 Visit** 被 `complete`（不是"生成"，是"真的去了"）；
2. 该 Visit 所属的 Day 通过 `evaluateDay()`，`structural ∈ {feasible, conditional}`；
3. 该 Trip 至少有 **5 个 item**（排除空壳测试数据）；
4. 该 Trip 不是站长自己的（通过 `memberId != owner` 或匿名标记过滤）。

**为什么是它：** 它同时约束了"有人用""行程是可行的""不是玩具"。生成数可以刷，访问量可以买，只有"真的走完一天"骗不了人。

### 10.2 分层指标

| 层 | 指标 | 90 天目标 | 12 个月目标 | 度量方式 |
|---|---|---:|---:|---|
| **获取** | 自然搜索 UV / 周 | 50 | 1,200 | 服务端日志（非 GA） |
| | 分享页打开数 / 周 | 20 | 500 | `share_viewed` |
| **激活** | 访问 → 生成转化率 | 8% | 15% | `trip_generated / page_view` |
| | 生成 → 导出/分享率 | 25% | 40% | `capsule_exported / trip_generated` |
| **留存** | 7 日回访率 | — | 20% | 匿名设备 ID（可关闭） |
| | 二次生成率 | — | 30% | `trip_generated` 去重 |
| **执行** | **VTE / 周** | **3** | **50** | 见 §10.1 |
| | 核验清单完成率 | 40% | 60% | `verification_done` |
| | 延误重排后改回率 | <50% | <30% | `trip_edited` after reorder |
| **信任** | 决策就绪点位数（莫斯科） | 40 | 120 | `evidence-coverage.mjs` |

### 10.3 埋点最小集

只采这 10 个事件，多一个都不加（避免"为了分析而分析"）：

```text
page_view          { page }
city_viewed        { city }
trip_generated     { city, days, engine, itemCount }
capsule_exported   { format, bytes, days }
share_created      { visibility }
share_viewed       { referrer }
guest_joined       { role }
item_completed     { delayMinutes, source }
verification_done  { field, result }
mcp_called         { tool }
```

**隐私红线：**

- 不采 IP（服务端日志只保留 24 小时，且聚合后删除）
- 不采精确坐标（只采 `placeId` 的城市级别）
- 不采设备指纹
- 不接第三方分析 SDK
- 设置页可一键关闭，关闭后本地缓存立即清空

### 10.4 反指标（出现即警报）

| 反指标 | 说明 | 阈值 |
|---|---|---|
| 点位数增长，但决策就绪点位数不增长 | 广度幻觉复发 | 连续 2 个月 |
| 测试数增长，但线上事故不降 | 测试的边际收益为负 | 季度复盘 |
| 页面数增长，但 7 日回访不涨 | 功能堆叠 | 连续 2 个月 |
| AI 调用增长，但生成→导出率下降 | AI 在制造垃圾 | 连续 1 个月 |
| 分享数增长，但 guest 加入率下降 | 分享的是"炫耀"不是"可用" | 连续 1 个月 |
| 数据覆盖率提高，但 unknown 被估算填充 | 诚信崩塌 | **一次即红线** |
| 单周工程时间 > 80% | 内容/分发被挤压 | 连续 3 周 |

### 10.5 度量节奏

| 频率 | 动作 | 产出 |
|---|---|---|
| 每周 | 看 VTE、生成数、导出数 | 3 行周记 |

**不做实时大盘。** 单人项目看实时数据只会焦虑，不会变好。

### 11.1 四个收入假设

理由：
- **H1 现在就能做。** 一个信任你内容的人，愿意为"帮我排 7 天俄罗斯"付 500 块。这不丢人，而且是最好的用户研究——你会知道他们真正在意什么。

- **H2 依赖流量。** 没有 5,000 MAU，订阅制是空谈。
- **H4 不做。** 一旦挂联盟链接，"可信"就有了利益冲突。

### 12.3 止损规则（if-then，写死，避免情绪化决策）

| 单月服务器成本 > ¥500 | 立即审计流量来源，防爬虫/盗链 |

### 12.4 一个必须写下来的判断

>
> 90 天内找到那一个人，比 12 个月内做完 P0–P5 更重要。

## 结语

这个项目已经证明了一件很难的事：**一个人可以用工程纪律，做出一个在正确性上超过大多数商业产品的系统。**

接下来要证明另一件更难的事：**这套系统值得被使用。**

前者靠能力，后者靠取舍。取舍的意思是——**放下"把旅行闭环做完"的执念，先把莫斯科的 40 个点位做到没人能挑错，然后让三个人带着一个文件走进那座城市。**

如果他们回来跟你说"幸好有这个"，平台就成立了。
如果没有，那就改，直到有。
