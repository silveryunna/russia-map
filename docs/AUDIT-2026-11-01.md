## 0. 总结判断

这轮迭代不是“只堆了页面”。Trip v2、稳定 ID、IndexedDB、迁移、时间轴、确定性可行性、可执行修复、资料核验管线、真实交通矩阵与密钥加密都已形成真实代码和测试，上一轮的多数地基问题已解决。

新的主要矛盾是：

> **系统的工程测试越来越绿，但“数据是否同源、结论是否可信、计划是否符合真实旅行”尚未达到同等成熟度。**

下一阶段不应继续沿着“再给生成器补一个规则、再给编辑器加一个按钮”的路径前进，而应完成三次转变：

1. **从功能完整转向数据完整**：统一 Visit 写入、存储原子性、完整 schema、跨标签页安全。
2. **从硬约束通过转向可信度可解释**：结构可行与事实覆盖分开呈现，未知不再被绿色结论吸收。
3. **从合成回归转向真实校准**：Today/Visit 薄闭环、实际耗时、实地误差和人工认可率成为下一阶段证据。

## 2. P0：下一阶段开始前必须解决

### A1. Visit 与打卡已经形成两个持续漂移的事实源

**证据**

- Trip 的 Visit 存在 IndexedDB `travel-trips`：`src/pages/trip/store.js`。
- `plan.js` 只在启动时执行一次 `migrateLegacy()`。
- 地图、清单、笔记仍通过 `src/modules/checkin.js` 读写 `localStorage['travel-checkin-v2']`。

因此，迁移之后的新打卡不会自动进入 Trip 的 Visit；行程页的历史记录与地图/清单将逐步不一致。P1 的“新打卡可关联 Trip”目前只有数据模型，没有统一写路径。

**影响**

计划—实际双时间线、个人节奏学习、真实动线校准都建立在不完整数据上。越晚统一，迁移成本越高。

**策略**

- 建立唯一 Visit repository 和读模型。
- 旧页面先通过适配层读取 Visit，并生成旧 UI 需要的派生状态；不要长期双写。
- 增加“地图打卡 → Visit → Trip 今日视图 → 备份导出”的同一条端到端测试。
- 迁移旧 localStorage 时保留原始备份，提供一次性对账报告。

### A2. 多标签页保存会静默覆盖，备份恢复也不是原子操作

**复现**

两个并发 `saveTrip()` 都读取“行程不存在”，随后各自写入 revision=1：

```json
{"aRevision":1,"bRevision":1,"final":"另一个标签页","revision":1}
```

`store.js` 的 get → increment → put 不是一个原子事务，也没有 Web Locks/BroadcastChannel。`importAll({mode:'replace'})` 先 clear 再逐条写入，中途失败会留下半恢复状态；merge 对同 revision 的不同内容只显示 skipped，没有冲突记录。

**影响**

同一浏览器开两个标签页就可能丢编辑；备份恢复失败可能破坏现有数据。未来的多设备同步会放大这个模型缺陷。

**策略**

- 单实体保存使用 readwrite 事务内版本检查；批量导入使用一个事务。
- 浏览器内用 Web Locks 串行化写操作，BroadcastChannel 通知其它标签页刷新。
- 同 revision 不同内容生成 conflict，不以 skipped 掩盖。
- replace 先完整校验、暂存并允许回滚，再替换正式数据。

### A3. “硬约束通过”与“事实可信”需要成为两个独立维度

当前 `feasible` 只表示无硬错误且有 timeline。unknown 日历保留宽边界并产生提示，这是正确的计算策略；但 CLI 仍显示“✅ 可行”，页面在只有 unknown、没有其它 warning 时也可显示“✅ 硬约束通过”。

真实例子：

- 地铁艺术巡礼 14/14 点位开放时间未知，结论仍为绿色可行。
- Day 2 有 6/8 开放时间未知，交通实测只有 2/7 段。
- 所有 38 个样板点的停留时长均为估算。

**判断**

代码没有直接把 unknown 当成已核实，但用户看到的总结仍容易被理解为“这天已可靠”。

**策略**

结果改为两个轴，不做不透明的综合分：

- 结构：`invalid / feasible / infeasible`；
- 证据：`verifiedCoverage / unknownHours / measuredDurationCoverage / matrixCoverage / staleFacts`。

UI 使用“结构上可排，但有 6 处待核实”而不是单一绿色。为每日提供“未知核验清单”，让 unknown 转化为可执行任务。

## 3. P1：领域与算法盲区

### B1. Schema 校验没有覆盖导入数据的关键字段

**复现**

一个固定日期 Trip 同时缺少 `endDate` 和 Day 日期，条目含 `startLocal:'not-a-time'`、`timeZone:'Not/AZone'`，只要将 confirm 标为 needs_confirm，`validateTrip()` 返回：

```json
{"ok":true,"errors":[]}
```

当前校验没有强制 fixed Trip 的 endDate/每日日期，也未校验 startLocal/endLocal/timeZone、actualVisitId 等引用。

**影响**

非法备份可进入正式数据库；未来同步会把错误传播到更多设备。

**策略**

先补完整契约和负例，再开放更多导入/分享能力。工厂函数的兼容默认值不能替代导入校验。

### B2. 交通矩阵与兜底估算的门到门口径不一致

`estimateLeg()` 的打车兜底加 `taxiOverheadMinutes=5`，命中 car 矩阵时直接使用 API driving minutes，不加同样的上下车/叫车开销。

复现实验：矩阵驾车 20 分钟，当前返回门到门 20 分钟；若采用兜底相同口径，应为 25 分钟。

**另一个问题**

矩阵把“真实路线”简写为“实测”。它实际包含：

- 第三方路线快照，不等于站长实测；
- 历史采集时的路线/路况，不等于当前实时路况；
- driving/walking，不代表公共交通。

现有动线矩阵覆盖约 65%，另有 p001→p002 的步行路线/直线距离比 4.3。该比值可能有真实围栏或入口原因，但当前质量门没有异常比值复核机制。

**策略**

交通段拆分 `access/wait/inVehicle/egress/transfer` 分钟，统一门到门口径；UI 区分“第三方路线 / 个人实测 / 模型估算”。为路线/直线比、速度和反向差异增加异常报告，而不是简单判错。

### B3. 生成器的目标仍偏“填满”，与留白和真实节奏冲突

`MIN_FILLED_DAY=5` 会主动补点；生成/迁移后的 visit 默认 `mustVisit=true`。结果是：

- 默认草案倾向每天尽量多点；
- 自动减负只删 `mustVisit=false`，多数生成点默认可删性不足；
- 真删除时又按停留从长到短，不等于“边际价值最低”；
- 页面虽已显示留白，但生成器没有把用户希望的留白当输入约束。

**策略**

引入三级优先级 `must/should/nice`，兼容旧 boolean；生成时标明核心动线点与补充点。以“轻松/均衡/丰富/摄影”作为意图配置，留白成为硬约束或明确目标，而不是事后展示的指标。

### B4. 特殊规则增长快，正在形成“启发式补丁 treadmill”

近期连续加入跨日去重、前看一步、半日线配对、稀疏日补点、任意位置插入、开门等待排序、真实矩阵等规则。每一步都有测试，这是优点；但 `engine.js` 已接近 400 行，`plan.js` 超过 1200 行，目标函数和特殊流程越来越难以理解。

**风险**

每修一个局部坏例就增加一条规则，最后只能证明既有测试没坏，无法证明整体计划更符合人。

**策略**

- 暂停新增启发式，先建立场景语料与人工评价集。
- 将“生成候选”和“评价候选”分离，用统一、可解释的目标向量比较方案。
- 输出 2–3 个 Pareto 候选（轻松/少走路/内容丰富），而不是不断调一个全局权重。
- 拆分 `plan.js` 的列表、编辑器、AI、导入导出和 Today 控制器，不借权重写框架。

### B5. 计划—实际双时间线仍只有迁移骨架

Visit 目前只有 date/dateSource/note/countIndex/source，缺少实际开始/结束、时间精度、跳过原因和实际交通段。页面没有统一的实际到访写入流程，因此无法计算个人停留误差或路线误差。

**策略**

先完成 Today + Visit 薄闭环，而不是直接开发“AI 个人画像”。实际时间允许只记录日期或大致时段，避免为了数据完整增加行中负担。

### B6. 跨午夜和时区模型还不能支撑完整多城旅行

Day 校验要求 `endTime > startTime`，无法表达 18:00–02:00；feasibility 不消费 Item.timeZone；绝对时刻只支持本地 `YYYY-MM-DDTHH:MM`，没有 UTC instant 或 offset。

当前适合单城日间编辑，不应把“跨午夜显示正确”误认为“跨日航班/多城时区已完成”。在预订与多城扩张前，需要先定义时间模型。

## 4. 验证与计划本身的盲区

### C1. 合成测试证明“不违规”，不证明“值得走”

49 个生成计划主要检查天数、硬错误和每日最少项，无法衡量：

- 用户是否需要大量删除/移动；
- 动线是否符合兴趣与体力；
- 等待和折返是否可接受；
- 数据 unknown 对结论影响多大；
- 实际执行与估算差多少。

**策略**

建立 20–30 个人工确认场景，记录编辑距离、人工认可率、实际误差和负面案例。每次算法变更必须比较指标，而不是只新增一个针对坏例的 if。

### C2. 核心移动端路径的 CI 仍不足

`tools/smoke-test.mjs` 对地图执行桌面+手机，但 `probePlan()` 只对桌面执行。行中最重要的手机编辑器、时间轴和触控拖动没有同等覆盖。

**策略**

增加手机计划编辑器、触控、离线、跨标签页和备份恢复测试；真机人工验收单独列出门禁，不能用桌面模拟替代全部体验。

### C3. 路线图状态已漂移且混入过多历史细节

v3 开头仍写“莫斯科开放时间 0、票价 0”，实际已为 12/38、6/38；P1 把“新打卡关联 Trip”写成已接页面，但目前只有一次性迁移；P0 的移动端/离线验收也未完全闭环。

1275 行文档同时混合长期愿景、当前状态、历史日志、schema 草案和检查表，继续追加会越来越难执行。

**策略**

- ROADMAP v4 只保留当前判断、下一阶段、长期方向和验收门。
- 历史细节留在 git/审计报告；当前数据指标由工具生成或引用报告。
- 状态区分“代码已落地 / 集成已完成 / 现场已验证”，避免一个 ✅ 覆盖三种成熟度。

## 5. 创造性策略与功能

### F1. 不确定性预算与条件式可行

不是给行程一个不透明分数，而是让用户看到：

- 哪些结论确定；
- 哪些地方未知；
- 未知最多影响多少时段；
- 出发前必须核验哪 2–3 件事。

进一步可提供“保守/均衡/紧凑”三种缓冲策略。unknown 不再只是黄色小字，而成为可管理的旅行风险预算。

### F2. 第一方“亲证路线图”（Witnessed Route Graph）

把用户确认过的实际段转化为交通证据：

```text
placeA → placeB / mode / actualMinutes / recordedAt / sampleCount / precision
```

第一方实测与第三方路线分开保存。多次样本用收缩估计回到类型默认值，避免一次排队就永久带偏模型。它能逐步摆脱 API 配额和公共交通数据缺口。

### F3. 行前压力测试与离线应急预案包

利用现有 repair/Plan B，不需要实时数据即可提前模拟：

- 周一闭馆；
- 上一站延误 45 分钟；
- 下雨；
- 体力只剩 60%；
- 打车预算翻倍。

输出少量“如果发生 X，就执行 Y”的离线卡片。相比行中临时请求 AI，这更可靠、更便宜，也更适合无网场景。

### F4. Pareto 行程卡与“留白权”

每次生成 2–3 个硬约束都通过的方案：

- 轻松：更多留白、更少点位；
- 顺路：更少折返和等待；
- 丰富：更多兴趣点；
- 摄影（数据成熟时）：保留关键光线。

明确展示取舍，不宣称唯一最优。用户可以选择“今天下午不安排”，系统不强行补到 5 项。

### F5. 行程 Diff 与影响链

每次编辑显示：变更前后、影响到的后续时间、预订、预算和离线包版本。后续同步、协作和“为什么今天超时”都复用同一 ChangeEvent，而不是分别实现。

### F6. 数据缺口即任务

把 Trip 实际用到的 unknown 自动生成“出发前核验清单”，按影响排序，而不是要求维护者补齐整个数据库。研究队列从“城市全量覆盖”转为“这次旅行的决策就绪度”。
