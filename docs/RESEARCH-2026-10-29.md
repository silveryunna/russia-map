## 0. 执行摘要

### 0.1 一句话结论

**源码重构已经把“能不能维护”这一层技术债还清了；现在的主要矛盾是“可执行旅行平台”跑在“以展示文案为主、可计算字段几乎为零”的数据与“只有草案、没有 Trip 聚合”的产品结构之上。**

具体说：

- 工程质量门是真实有效的：626 点位、28 动线、26 个变异、坐标 0.065m 基线、ESM 严格解析、src/产物一致性全部通过。
- 但莫斯科 278 个点位中，**开放时间 0、票价 0、官网 0**；全库仅 4 个 `hours`、7 个 `ticket`、1 个 `url`。
- 现有“计划”仍是 `travel-plans-v1` 草案：按点位名称引用、跨动线重复、无时长/交通/开放日历、无 Trip/Visit/预订/费用实体。
- PWA 有 Service Worker，但瓦片缓存域名与实际底图不一致；“有 SW”不等于“地图可离线执行”。

因此，平台化的正确顺序不是“加更多 AI/页面/城市”，而是：

> **先建立“事实 → 行程 → 执行 → 实际反馈”的数据闭环，以莫斯科 30–50 个核心点位和 5–8 条真实动线为样板，再让确定性引擎消费这些数据。**

### 0.2 本次核验的五个关键事实

| # | 事实 | 证据 |
|---|---|---|
| 1 | 工程质量门全绿 | `check-data` 626/28/13；`coords-test` 4/4，最大差 0.065m；`mutation-test` 26/26；`check-esm` 通过；`check-build-sync` 26 个 bundle 全对上 |
| 2 | 开发服务器仍不可用 | `vite root=src` 且无 `publicDir`/代理，`/data/points.json` 返回 200 `text/html`（index.html），前端 `r.json()` 直接报错 |
| 3 | 计划引擎仍会跨动线重复 | `src/pages/plan.js:63-66` 把每条动线整段加入，未按已用点位过滤；`distribute()` 把放不下的点全部追加到下午 |
| 4 | 莫斯科没有排程事实 | 278 点中 `hours=0`、`ticket=0`、`url=0`；全库 `hours=4`、`ticket=7`、`url=1` |
| 5 | 离线承诺不完整 | `sw.js:25-27` 只匹配 `tile.openstreetmap.org`，实际底图是 `tile.openstreetmap.de`、Esri、高德/腾讯、天地图；前四类不会进入 4000 块运行时缓存 |

### 0.3 对旧版研究的三项修正

1. **不是“没有计划”**。`plan.html` 已有本地计划、规则引擎、AI 生成和 Markdown 导出；缺的是“可编辑、可执行、可关联预订/费用/打卡”的 Trip 聚合，而不是从零做一个计划页。
2. **离线导航和黄金时刻不是空白市场**。Organic Maps / OsmAnd 已把通用离线导航做得很成熟；PhotoPills / PlanIt 已把天文时刻做到专业级。机会在于“与本项目点位、真实动线、证据体系、行程执行联动”，而不是单点首创。
3. **“先排程、后补数据”应反转**。没有开放日历、停留时长、路段耗时和来源时间，优化器只会给未知信息套一层精确外观。先做数据契约与一个城市的深度覆盖，再上求解器。

### 0.4 建议定位

> **本地优先、证据可追溯、离线可执行的旅行知识与行程平台；第一阶段聚焦中国出境游的俄罗斯/中亚长尾目的地。**

不做另一个 Wanderlog，不做 OTA，不做通用导航。差异来自四种能力的组合：

- 自有、可核验、可持续复核的地点知识；
- 计划与实际并行的旅行时间线；
- 弱网/离线仍可执行的行程包；
- 从真实执行反馈中持续变准的个人节奏与内容资产。

### 1.2 现有真实能力

- **前端**：原生 ES Module + Leaflet + Vite 多页应用（9 个入口），地图页已拆为 `coords/icons/layers/nav/overlays/player/ratings` 等模块。
- **数据**：626 个点位、28 条动线、59 个点位/66 条评分快照、第一方评分体系（私人米其林）。
- **地图**：多底图、双坐标系补偿、点位筛选、动线播放、定位与距离排序、聚合、遮罩、覆盖层、全屏。
- **计划**：`travel-plans-v1` 本地保存，规则/AI 双通道，Markdown 导出。
- **打卡**：`travel-checkin-v2` 保存次数、日期与一句话感想，但仍是全局点位状态。
- **协作**：账号、投稿、审核、照片上传、AI 配额与用量台账。
- **PWA**：页面和同源资源网络优先，具备运行时缓存。
- **运维**：`npm run publish` 一键发布；服务器 cron ≤2 分钟追平；GitHub Actions 质量门 + 6 小时站点监控；天地图 Key 服务端化。

### 1.3 仍未修复的确定性缺陷（按影响排序）

#### A1. `npm run dev` 仍不是可用的开发路径（已实测）

`vite.config.js` 以 `src/` 为根，未配置 `publicDir` 或 `/data` 代理；页面请求 `./data/points.json` 时，Vite 返回 200 的 `index.html`，前端 `r.json()` 报：

> `Unexpected token '<', "<!doctype "... is not valid JSON`

实测：`http://localhost:5199/data/points.json` 返回 `200 text/html`，大小 2741 字节。  
影响：新开发者按标准命令启动后无法开发地图/计划；AI 助手也容易误判为数据损坏。  
建议：在 Vite 中提供 `data/content/photos/api` 的开发映射或代理，并把 `plan.html` 纳入冒烟。

#### A2. 规则引擎存在跨动线重复与超负载（已核验）

- `src/pages/plan.js:63-66`：每条动线完整加入日程，`ids.forEach(p => used.add(p.id))` 只登记已用，**没有先过滤掉已用点位**。
- `src/pages/plan.js:102-106`：上午/下午放不下的点全部 `push` 到下午。
- 实测数据：至少 8 个点位跨动线重复（如“老阿尔巴特步行街 + 维克多·崔纪念墙”出现 3 次，“莫斯科大剧院（芭蕾）”2 次）。
- 未根据开放日、路程、停留时长、体力做判断。

**结论**：现有规则引擎适合生成“候选清单”，不应标注为可直接执行的日程。

#### A3. 计划以点位名称而非稳定 ID 引用（已核验）

`src/pages/plan.js:102-106` 在 slots 中保存 `p.name`；详情页 `byName.get(n)`（`:299`）与导出 `byName.get(n)`（`:336`）再反查。`data/routes.json` 的 `steps[].point` 同样按名称索引。  
影响：点位改名、双语名调整、同名点都会使历史计划出现死引用。  
建议：先建立 `name → placeId` 映射并迁移，名称只作显示快照。

#### A4. 本地计划存储缺少容错与版本迁移（已核验）

`src/pages/plan.js:16` 在模块顶层直接 `JSON.parse(localStorage.getItem('travel-plans-v1') || '[]')`。  
影响：损坏数据会导致整页无法启动；没有 `schemaVersion`、迁移函数、备份或跨设备恢复。  
建议：复用 `checkin.js` 的旧键迁移思路，增加 `schemaVersion`、损坏备份和恢复入口。

#### A5. 前后端天数约束不一致（已核验）

前端允许 1–14 天（`src/pages/plan.js:213,239`），服务端限制 1–7 天（`api/index.php:299`）。8–14 天的 AI 请求会静默缩水。  
原则：约束必须来自共享契约，前后端不能各写一份。

#### A6. AI 失败后的自动规则回退会模糊结果来源（已核验）

`src/pages/plan.js:285-293` 在 AI 失败后自动生成规则计划。toast 会提示失败，但用户最终仍得到一份计划，容易忽略它已经不是 AI 结果，也无法选择重试、编辑约束或仅查看错误。  
建议：明确提供“重试 / 使用离线规则 / 取消”，并保留失败原因和结果来源。

#### A7. PWA 实际瓦片缓存规则与底图域名不一致（已核验）

- `sw.js:25-27` 的 `isTileUrl()` 只匹配 `tile.openstreetmap.org`。
- 实际底图：`src/pages/map.js:683` 用 `tile.openstreetmap.de`；`:677-681` 用 Esri；`src/pages/map/layers.js:78-88` 用高德、腾讯、OSM.de、天地图。
- 结果：OSM.de、Esri、高德、腾讯瓦片不会进入 4000 块运行时缓存；天地图 `/tdt/` 属同源，会被同源分支缓存。

**影响**：“有 Service Worker”不等于“地图可离线执行”。平台需要显式离线包清单、容量预算、版本与真实飞行模式测试。

#### A8. 测试仍聚焦地图，计划与 API 缺少持续回归（已核验）

- CI 的 Playwright 只加载 `map.html`（`tools/smoke-test.mjs`）。
- 规则引擎没有黄金样本/属性测试；PHP API 没有本地测试套件；CI 不跑 PHP lint。
- `tools/api-smoke.mjs` 是线上全链路脚本，需要凭证并写入测试数据，不等于每次提交都能运行的单元/集成测试。

优先补：计划引擎不重复/不重叠/不超限/引用有效；迁移与损坏存储；plan/list/notes/friend/account 关键路径；API 认证/授权/配额/导入/SSRF/事务。

#### A9. 自定义 AI 接入仍有平台级安全边界要补（部分已缓解）

- `api/index.php` 的 `ssrf_check()` 先 `gethostbyname()` 检查 IP，但 cURL 请求时会再次解析 DNS，存在 DNS rebinding 绕过检查的理论空间；`CURLOPT_FOLLOWLOCATION=false` 已挡住重定向绕过。
- `ai_settings.api_key` 在 SQLite 中以明文保存（`api/index.php:24-25,428-430`）；但接口只回 `has_key`，不再回显明文（已缓解）。
- Bearer token 长期保存在 `localStorage`（`friend-token`/`admin-token`），7 天有效；CSP 与转义降低了 XSS 风险，但不是零。
- 已有防线：登录限流、投稿配额、幂等键、图片 MIME/大小校验、HTML 注入拦截、Key 不进前端。

**结论**：个人小站阶段风险可控；若保存护照、票据、家庭地址、实时位置，现有安全与隐私模型不够。平台化前需重新划分数据等级、加密边界与凭据存储方式。

#### A10. 文档与实现仍有漂移（已核验）

- `AGENTS.md` 的 CI 注释仍写“21 变异”，实际已是 26。
- `README.md` 仍主要介绍静态预览，而 `npm run dev` 不能加载数据。
- `MAINTENANCE.md` 与实现大体一致，但部分“已知遗留”需要定期复核。

文档数字不应成为人工重复维护的事实源。

#### A11. PWA 外壳未预缓存关键页面（已核验）

`sw.js` 的 `SHELL_ASSETS` 只含 `index/map/list/notes/album`，不含 `plan/friend/account/admin`。这些页面首次访问前不在缓存中，离线时可能无法打开。  
建议：按“行中真正需要”的页面清单预缓存，并区分“可离线只读”和“必须联网”的页面。

#### A12. 数据可计算性不足（已核验，见 §1.4）

莫斯科 278 个点位中 `hours=0`、`ticket=0`、`url=0`；全库仅 4/7/1。计划引擎即使想排时间，也没有字段可用；AI 上下文还被服务端裁剪为 `name/type/cluster/highlight/tags`（`api/index.php:344-346`），根本拿不到开放/票价信息。

### 1.6 审计结论

> **工程债已还一层，产品债与数据债是主矛盾。**

- 可维护性：源码、构建、部署、质量门已达标。
- 可执行性：计划仍是草案；没有 Trip/Day/Item/Visit；没有时长、交通、开放日历。
- 可信性：没有来源、采集时间、有效期；`unknown` 不是一等状态。
- 离线：有 SW，但没有离线包清单、容量预算、真实飞行模式验收。
- 运营：有监控，没有数据复核、错误追踪、备份恢复。

下一阶段不应以“页面数量/点位数/城市数”作为进度，而应以“**一份可恢复、可编辑、引用稳定、事实来源清楚的莫斯科 Trip，并完成一次真实旅行**”作为退出条件。

## 2. 市场结构：不是一条赛道，而是四层

### 2.1 四层结构

| 层 | 用户购买的核心价值 | 代表 | 本项目不应硬拼 |
|---|---|---|---|
| L1 记录/回忆 | 轨迹、照片、旅行书、足迹 | Polarsteps、AdventureLog、高德足迹 | 原生后台轨迹、电池优化、照片云 |
| L2 编排 | 地图 + 逐日 + 预订 + 预算 + 协作 | Wanderlog、TREK、穷游、马蜂窝 | POI 全量覆盖、实时协作成熟度 |
| L3 交易 | 机票/酒店/门票/支付 | 携程、飞猪、Google Flights | 票务库存、支付、退改签 |
| L4 执行保障 | 航变提醒、离线导航、行中帮办 | TripIt Pro、飞猪帮办、Organic/OsmAnd | 通用路网、实时客服 |

跨层者极少，多数靠跳转缝合。本项目的自然位置是 **L2 + L4 的组合**：编排 + 执行保障，而不是 L3 交易。

### 2.4 2025–2026 的产品趋势

1. **AI 从“生成”转向“执行”**：飞猪帮订/帮办、Google AI Overviews 直接导出 Docs/Maps 列表；用户不再满足于“给我一份漂亮行程”。
2. **Local-first 与自托管回归**：TREK、AdventureLog、Organic Maps 都在强调数据留在本地/自己的服务器。
3. **离线从“缓存”升级为“一等公民”**：TREK 有整站离线开关；Organic Maps 以“不发送一个字节”为卖点。
4. **隐私成为卖点，也成为事故源**：行程天然包含住址、航班、护照、费用、实时位置；公开分享必须默认脱敏。
5. **AI 信任开始反噬**：2026 年已出现“AI 行程踩坑”的集中报道；可核验、可解释、可回退比“更会生成”更重要。
6. **中国出境游恢复，但工具仍按“信用卡 + 英语 + 西欧”假设设计**：俄罗斯/中亚的支付、网络、语言、签证、登记规则是明显空白。

### 2.5 尚未被很好满足的五个空位（按与本项目资产匹配度排序）

1. **目的地事实卡**：可核验的开放时间/票价/预约制/闭馆日 + 变更时间戳。  
   本项目已有 626 点、9 城、`confidence 100/75`，缺的是 `as-of`、来源、有效期与复核队列。
2. **离线行中执行**：无网可用的一日动线 + 打卡 + 票据 + 应急信息。  
   本项目已有 PWA、localStorage、双节点，缺的是离线包清单、容量预算、真实飞行模式验收。
3. **中文长尾目的地结构化数据（俄/中亚）**：OSM 有地理无内容，OTA 有交易无深度。  
   本项目的莫斯科/圣彼得堡/阿拉木图内容与真实动线是稀缺资产。
4. **多源评分的第一方口径**：跨源归一 + 可信度标注 + 私人米其林。  
   现有 59 点/66 条评分是雏形，但还没有来源、采集时间、维度解释与展示纪律。
5. **数据新鲜度可视化**：字段级 `as-of` 与来源，让用户知道“哪些已核实、哪些该复核”。  
   可直接借鉴 ticket-monitoring 的四态一致性。

额外的两个高价值空位：

6. **同行者异步决策层**：投票、分工、AA 结算、评论，不要求所有人安装 App；微信分享即可参与。
7. **送签级行程单**：签证/邀请函/移民卡/登记要求下的结构化行程 PDF，直接可用于送签与入境查验。

### 2.6 中国出境游（俄罗斯/中亚/欧洲）特有的未被满足需求

- **支付与网络断点**：俄境内 Google/部分国际支付不可用，Mir/UnionPay/现金并存；离线不是加分项，是刚需。
- **签证与入境材料**：邀请函、移民卡、落地登记、保险、往返机票；行程单需要“送签级”格式与完整性校验。
- **中文名与西里尔地址对照**：复制到 Yandex Maps / 2GIS 能直接搜到；英文名不够。
- **俄铁与长途卧铺**：RZD 时刻、跨时区、夜间车、到达日安排；通用产品几乎不建模。
- **现金为主的多币种分账**：卢布/坚戈/欧元/人民币；汇率冻结、最大余数法、退款。
- **安全与语言**：使馆/急救/报警电话、警察查验、常用俄语短句、着装与礼仪。
- **家庭/朋友同行**：长辈不装 App、只看看今天安排；微信群分享链接比“邀请注册”更现实。

这些不是“内容栏目”，而应进入领域模型：`Assertion(kind=visa/payment/safety/transport/language)`、`Document`、`Reservation`、`Expense`、`ShareProfile`。

## 3. 六个指定项目：代码级拆解

> 版本与许可以本地浅克隆/仓库 LICENSE 为准；星标只说明关注度。所有“借鉴”均为架构思想，任何代码复用前必须单独做许可证评审。

### 3.1 TREK：成熟的平台领域模型与“真实账务”细节

**基本信息**：TypeScript，npm workspaces 三包结构；server 为 NestJS 11 + MikroORM 7 + better-sqlite3（87 个 nest 模块、162 实体、328 个 migration），client 为 React 19 + Zustand + Leaflet，shared 用 Zod 定义全部请求/响应与 WS 事件，双端同源。约 15.2k★，AGPL-3.0（`plugin-sdk` 单独 MIT）。测试规模：server 约 1187 个测试文件/1.9 万用例、client 约 1356 个/1.8 万例、shared 234 个/2469 例；CI 7 分片 + 覆盖率合并、Playwright Chromium+WebKit、20 余个 ratchet（size/boundary/tx/RTL/offline），属重工程化样本（静态计数，非本轮执行）。

**源码证据**

- `shared/src/trip/trip.schema.ts`：Zod 契约；`date_shift_mode` 明确 `keep_bookings` / `shift_all`（`:112-116`）。真正的日期语义在纯函数 `shared/src/trip/day-grid.ts:197-246`：有日期的第 n 天取新区间第 n 个日期，缩短时从尾部整天删除（连内容），无日期天只删空白天，被删的以 `removedDays` 回传。
- 改期实现：默认模式按绝对 `reservation_time` 重锚定预订（`reservations.service.ts:343-362`），`shift_all` 则整体平移（`trips.service.ts:525-537`）。**风险点**：缩短行程会直接删除溢出日内容（`day-grid.ts:183-195`），对“计划—实际”时间线不可接受。
- Trip 支持无账号 guest member（`is_guest=1` 的 users 行，永不可登录，`trips.service.ts:113-125`），适合家人/朋友，而不是强迫注册。
- 预算：`total_price` 为 double + currency + `exchange_rate`，入账时冻结汇率，`1` 表示未冻结（`budget.service.ts:300-355`）；换币整体 rebase（`:441-499`）；分摊用整数分最大余数法（`budget-money.helpers.ts:115`）。缺汇率不猜。
- 导入：`booking-import.service.ts` 先 preview 不落库（`:95-105`），AI 结果始终 `needs_review`（`:235`），无法定位的车站保留并警告（`:166`），确认后按项事务保存（`:302-305`）。
- 分享与离线：`ShareTokens` 以字段为 scope（map/bookings/packing/budget/collab/travel_only/hide_images），90 天过期，公开接口 `GET /api/shared/:token` 只回白名单列（`share.service.ts:245,332-410`）；ICS 订阅 token 可轮换/停用；离线包 `GET /trips/:id/bundle` 是 viewer 作用域的只读快照（`trip-read-model.service.ts:103-120`）。
- **可信度是明显短板**：`Places.opening_hours` 存了 OSM 原文却从不参与校验（`Places.entity.ts:58`）；只有 `needs_review` 0/1 与 `ingest_state`，无字段级来源、无未知态枚举。这是它与 FloatTrip 差距最大处。
- 权限：全局四档 admin>trip_owner>trip_member>everybody（`shared/src/permissions/permissions.ts:10-13`），**trip 内无角色**，member 默认可改一切（删除/分享除外）。

**应借鉴**：shared 纯函数 + 契约包（day-grid、ICS、权限表）双端同源；日期变更两策略；预览→人工确认→事务写入；冻结汇率 + 整数分 + 换币 rebase；share token 分域 scope 与 viewer 作用域离线 bundle。  
**不应照搬**：162 实体/87 模块/328 migration 的微模块化（PHP 小后端消化不起）；改期删溢出日内容；全局权限表 + 无 per-trip 角色的粗粒度协作；4 万测试与 ratchet 体系的维护成本。  
**许可边界**：AGPL-3.0，网络服务修改须开源；自托管不触发分发义务，但把代码搬进本仓库即被传染。只借鉴思想。

### 3.2 FloatTrip：真正值得学的是“未知状态 + 独立校验”

**基本信息**：Python/FastAPI + LangGraph 1.2 + OR-Tools CP-SAT，前端 React 18 走 CDN Babel 免构建。约 72★，仓库**无 LICENSE**（默认保留所有权利，只能学设计）。测试：31 个 pytest 文件约 190 例，另有 eval harness 22 例、5 个前端 node 测试；**Python 回归不在 CI**（CI 只跑 mobile-app jest/typecheck 与 openapi diff）。

**源码证据**

- 模型极简：没有 Trip/Day/Item 实体表，只有 `itineraries`（`plan_json` + `planner_state_json` + `parent_id` + `lock_version`，`app/core/database.py:39-52`）。版本树靠 `parent_id`，并发靠乐观锁（冲突返回 409）；日期只存 ISO start/end，天序号由 start+day-1 推导（`nodes.py:1037-1040`），**改期即整份重规划**，无增量迁移。预算只是自由文本；无 per-trip 时区（聊天上下文硬编码 Asia/Shanghai）；无成员/guest。
- `app/planning/optimizer.py`：候选池 12–24；`x[i,day]` 选日 + `AddCircuit` 建开放路径（`:399-419`）；开店区间与午/晚 45 分钟窗口（`:450-466`）；转场 `max(20, 高德 edge)`（`:508`）；14 项线性目标、scale 6000。求解 1 秒、单 worker、固定种子（`:576-580`），常止于 FEASIBLE，gap/bound 写入 diagnostics。
- 三级回退：硬最小点数 → 放宽最小重解 → 贪心 + 排列枚举（`:335-345,642-722`）；仍不可行就报错。
- `validate_solution()`（`:757-870`）独立重算目标并要求 |Δ|<1e-6，逐条硬约束码（`:773-836`）；绕路比只作诊断不作门（`:856-862`）。这是“求解器说成功不算成功、校验器复算才算”的范本。
- `app/planning/reliability.py`：`known/partial/unknown/closed` 四态，解析不了即 unknown 并保留保守边界（`:77-188,211-212`），采集时间缺失记 `not_provided`。
- 交通证据按 from/to/mode 存，带 `status=estimated|unverified`、`queried_at`、`expires_at`（驾车 900s、步行 86400s，`grounded.py:258-274`）；最终 `validation_summary` 三态 supported_checks_passed / needs_verification / failed。
- **真实局限**：距离全程 haversine，默认 variant A 根本不查高德路径；C2 才引入真实公交/驾车，实测上海 C1 10/18、C2 7/18，未达门槛仍是实验（`docs/c2-reliability.md`）。可信度体系只在 variant C 生效。
- 无分享、无导出；只有对话、历史、基于旧行程再生新版本，以及 `PUT /timeline` 手动编辑（服务端重算距离与午晚覆盖）。

**应借鉴**：①候选池“LLM 只出语义、服务端补权威字段”+ sha256 fingerprint 可复现（`candidate_builder.py:102-215`）——迁移成本低，正好接 626 点位；②求解后独立复算校验器 + diagnostics——可移植成 Node 纯函数；③未知态枚举 + 证据 TTL——与现有 `confidence` 兼容。  
**不应照搬**：planner-reviewer 3 轮 + time_check 3 轮的 LLM 自纠（贵且不可重复）；CDN Babel 免构建；把开放时间正则解析塞进求解核心（源文本一变更就整段 unknown）。  
**许可边界**：无 LICENSE，默认不可复制、修改或再发布；法律边界比 AGPL 更严。

### 3.3 Travel-Plan-Page：公开版是“编译产物”，不是手工删隐私

**基本信息**：JavaScript（纯 ESM，无框架），约 152★，仓库 LICENSE 为 MIT（GitHub API 标 NOASSERTION）；边界数据属 Natural Earth/geoBoundaries/OSM ODbL，模板底图另有出处。

**源码证据**

- canonical 层 entities 以稳定 ID 为键、值内不重复 id；行程项只存 `placeId/placeIds/ticketIds`，名称匹配被降级为 legacy warn（`scripts/validate-generation.mjs:314-317`）。
- 缺失是显式状态：`status:"missing"` 必须带 `title+missingFields+issueIds`，否则编译抛错（`scripts/compile-travel-data.mjs:161-176`）。
- 删除发生在数据层：`collectVisibleReferences` 只从可见路径收集实体（`:526-616`），关闭模块的分支直接输出空数组（`:639-712`）。
- 证明方式：全关模块后断言 `flights/places/regions/issues` 全空，且 `Synthetic hidden address` 不出现在输出（`scripts/test-generation-pipeline.mjs:119-144`）；改冻结文件触发 `integrity.core-modified`（`:56-63`）。
- **真实漏洞**：lite 管线不删数据。`SKILL.md:127` 明确“模块关闭时保留空数组”，`validate-lite.mjs:123` 只在 enabled 时检查有数据；因此 lite 产物里被关闭模块的真实数据会随 `trip-data.json` 原样发布。这是“双管线”带来的真实风险。
- 模块清单三处不一致：config schema 含 `tickets`，lite schema 与 UI 只有六个，脚本按七个处理（`compile-travel-data.mjs:7`）。

**应借鉴**：ID-only + 可见性闭包编译（关模块=删数据而非 CSS 隐藏）；全关模块的负向断言；空白底板 + uninitialized 状态机；冻结完整性。  
**不应照搬**：双管线、七模块 + 门票 + 记账 + D1 的组合复杂度。  
**许可边界**：MIT 可复用代码，但地图边界/底图有独立许可，不能按 MIT 直接搬运。

### 3.4 personalized-travel-guide-skill：内容供应链，不只是提示词

**基本信息**：Python + 单一 canonical HTML，约 78★，MIT。126 个 Python 文件、56 个测试文件；测试函数以 unittest/pytest 风格为主。

**源码证据**

- `assets/research-pack-contract.json` 定义统一研究包契约：`transport.status`、`stays[].status`、`place_id`、`practical_note`、`time_guard`、`shooting_plan` 等。
- `references/content-model.md`：`source_url` + 可选 Google 评分 + 检索日期；缺评分不算缺口（`:39,65,115,122`）。
- 内容最低量：4 个小吃、≥24 条准备项、5 折×4 主题、≥6 家餐厅（`scripts/validate_research_pack.py:149-173,214-219`）。
- place 必须有 `id/type/display_name/map_query/source_url` + 数值坐标且禁城市质心（`:92-105`）。
- 三层 sha256 冻结：plan/pack/profile 写入 `RESEARCH_PROVENANCE.json`（`scripts/compile_destination_profile.py:127-129`），可反查。

**应借鉴**：pack 的“固定数量 + 字符下限”可验收标准；plan/pack/profile 三层 sha 冻结；参照地污染词黑名单（可直接用于俄罗斯站防“三亚/日本模板”残留）；单 HTML 公开版。  
**不应照搬**：271 个文件、100+ 测试的维护面；对模板做字节级 CSS/JS 比对会让任何改版都判死。  
**许可边界**：MIT；GSAP/Tailwind 保留上游条款，用户图片不随 MIT。

### 3.5 travel-agent：安全边界需要诚实说明

**基本信息**：TypeScript/pnpm monorepo（core/server/web/desktop/browser-cli/skills），约 51★，Apache-2.0。

**源码证据**

- `packages/browser-cli/src/executor/payment-gate.ts`：对“立即支付/提交订单/pay now”等可访问名称做拦截，并明确注释：这是普通自动化路径的 guardrail，**不是安全边界**（`:8-12`）；不知道控件名称时放行（`:72-74`）。
- 真正的边界在 vault：字段分 L1/L2/L3，L3（CVV、支付密码、passkey）无任何覆盖开关（`packages/desktop/src/vault/tiers.ts:13-22`）；站点密码单独存储且“永远没有 reveal()”，只能 `useForFill` 后擦除（`browser-import/credential-store.ts:23-30`）。
- 写面用枚举而非采样：`executor/write-gate.ts:50-74`；交接期拒写、secret phase 连读都拒（`test/write-gate.test.ts:95-180`）。
- 行程契约薄弱：Trip 是磁盘目录，`trip.json` 由 app 写、`itinerary.md` 由模型写、`places.json` 仅约定；行程是自由 Markdown，服务端只读，无 schema、无 ID 关联，地点靠 name + lng/lat（`packages/skills/skills/trip-workspace/SKILL.md:36-41,170-180`）。

**应借鉴**：“点击即授权”+七字段确认卡；枚举写面；凭证分级与不可投影。  
**不应照搬**：CDP relay/Electron/扩展三端成本；实时 agent + 200 turn 预算与静态 PWA 无长驻进程的形态冲突。  
**许可边界**：Apache-2.0；browser-cli 为 vendored 上游，再分发须保留 NOTICE 与变更声明。

### 3.6 ticket-monitoring：数据健康比“采到了”更重要

**基本信息**：Python 单进程，约 301★，Apache-2.0。487 个测试文件、约 3,700 个 `test_` 函数（两次静态统计为 3,665–3,682，差异取决于是否计入参数化用例；均为静态计数，非本轮执行数）。

**源码证据**

- 架构：`main.py`（约 2454 行）调度与推送，`webui.py`（约 26797 行）把 HTTP/前端/API 塞进一个文件，`report.py`（约 3509 行）渲染推送长图，`crawlers/` 五渠道，`core/` 20 模块。
- 数据模型：`FlightPrice` dataclass 带 `prov` 字段存“入口/路径级证据 JSON”（`core/models.py:16`）；SQLite 四层：原始明细、日聚合 OHLC、请求级证据 `fetch_paths`（含 http_status/rows/evidence_level）、告警基线。
- raw→解析→展示一致性：解析行 ⇄ 原页镜像(raw) ⇄ RAW 路径，四态 `一致/未供/未采/不一致`（`webui.py:7635`）；镜像从同一条 raw 行结构重绘，“缺键一律标未供”（`:7838`）。
- 状态建模区分六种“缺失”成因：渠道级 `ok/part/fail/maint`，外加 `empty`（原站明确无符合条件的航班，不是失败）、`login_required`、`challenge`（`core/health.py:8-13`）。
- 判定分档单源：`_TIER_TABLE` 同时投影全词/短词/转写词/emoji 四列，`tier_dot()` 被五处消费点共用，`NEAR_RATIO=0.10` 单源（`alerter.py:25,97,140`）。
- 测试是“事故断言”而非覆盖率装饰：`tests/test_consistency.py:37` 逐参全等断言，`test_push_align.py:169` 连“≤20 全角”都进断言。

**应借鉴**：`prov` + `fetch_paths` 让每个展示值可回溯到某次具体请求；语义单源 + 多投影；把“未供/未采/需登录/空结果/补位/过期”建成阳性状态并定义“能否参与判定”。  
**不应借鉴**：五渠道登录态抓取与验证码人工接管（ToS/反爬风险）、分钟级轮询 + 电话/短信强提醒的成本结构、2.7 万行单文件。  
**许可边界**：Apache-2.0，可复用代码但需保留 NOTICE；其采集对象与合规风险不应带入。

### 3.7 横向综合：六个项目教给我们什么

| 主题 | 最佳参考 | 本项目应落成的能力 |
|---|---|---|
| 共享契约 | TREK 的 Zod schema | JSON Schema 单源，生成前端类型/PHP 校验；约束不再各写一份 |
| 日期/金额语义 | TREK 的 `date_shift_mode`、最小货币单位、最大余数法、冻结汇率 | Trip 日期变更策略；费用整数记账；缺汇率显示“未折算” |

| 公开编译 | Travel-Plan-Page 的可见性闭包 | 私有完整版/公开脱敏版从同一事实源编译；负向断言 |

## 4. 补充高星与垂直工具

### 4.1 AdventureLog（3.8k★，GPL-3.0）

- `CollectionItineraryItem` 通过通用引用关联 Visit、Transportation、Lodging、Note，把“内容是什么”与“排在哪天、什么顺序”分开；`Visit` 支持同一地点多次访问；交通有起止时区；公开 Collection 会校验关联内容是否可公开。
- **借鉴**：多实例访问、计划位置与内容解耦、公开传播的一致性校验。
- **警惕**：过度通用的引用会削弱数据库约束；本项目应采用显式 item 类型 + 统一校验，而不是无限泛化。

### 4.2 见好旅行路书（414★，MIT）

- `validate_trip_data.py` 把 schema 变成 V01–V22 可执行规则：全局 ID、引用类型、包含关系成环、枚举、日期/时区、费用三态、跨日班次、时长自洽、门票使用日等；同时提供生成、路线注入、最终 HTML 检查和 desource 脱敏工具。
- **借鉴**：中文旅行语义、跨日/时区校验、完整示范与必败反例、最终成品检查、送签级输出。
- **边界**：路书生成器不是行程运行时，但非常适合作为公开分享编译器/送签行程单的参照。

### 4.3 Organic Maps（15.8k★）与 OsmAnd（6.1k★）

- 两者均是成熟、活跃的高星项目。对本项目更合理的集成顺序：
  1. 导出标准 GPX/KML/GeoJSON；
  2. 提供 Organic Maps/OsmAnd/Yandex Maps/2GIS/Google/高德的外跳；
  3. 只为本项目特有需求补充“点位知识、摄影、文学、地铁艺术巡礼”图层；
  4. 确有用户验证后，再研发城市级离线路网包。
- **重要边界**：OSM 官方瓦片使用政策不允许大规模预下载；离线包若用栅格瓦片，必须自托管/使用允许离线分发的供应商，或改用示意图/矢量包。不要用“缓存 4000 块 OSM 瓦片”作为离线承诺。

### 4.4 PhotoPills / PlanIt

- 单点太阳方位、蓝调时刻和摄影规划已有专业工具。本项目的机会是：当一个点位因天气、闭馆或上一站延误而移动时，整个行程的机位时刻能联动重排，并保留摄影优先级——这是“行程执行”差异，不是天文算法差异。
- 先人工确认 10 个机位的朝向、光线和约束，与 PhotoPills/PlanIt 交叉验证；不要从 `highlight` 批量猜测后当成事实。

### 4.5 其他值得关注

- **RoadbookMaker**（社区提及）：无 Key、无登录、纯前端路书，形态最接近“单文件路书”；但本轮未能稳定核实仓库元数据，暂不作为主要依据。
- **穷游行程助手**：中文出境游送签场景的经典产品，但内容老化、产品刚回归；其“行程单可直接送签”仍是刚需。
- **马蜂窝/飞猪/携程**：强在内容/交易，弱在结构化、可离线、可追溯；本项目应做它们的“执行层补集”，而不是正面竞争。

## 6. 本项目盲区清单（按优先级）

### B1. 把“字段存在”误认为“数据可用于计算”（最高优先级）

626 点全部有 `highlight`，614 个有 `note`，但莫斯科 0 个 `hours/ticket/url`；没有逐点停留时长、入口时区、规则化营业日历、真实路段耗时。  
**后果**：直接上 CP-SAT/AI Agent 只会制造“看似精确、实则不可验证”的行程。  
**对策**：引入 `Assertion/Provenance`；先做莫斯科 30–50 个核心点与 5–8 条 ground truth 动线的完整覆盖；允许 `unknown`。

### B2. 计划与实际是两条未连接的时间线

计划存 `travel-plans-v1`，打卡存 `travel-checkin-v2`，照片/笔记另存；无法回答“这天原计划是什么、实际做了什么、为何变化、下次怎样更准”。  
**对策**：Trip 聚合下同时保存 planned item 与 actual visit，以关联而非覆盖的方式记录变更。

### B3. 行程不是只有点位：交通、住宿、预订、文件是一等实体

旧规划仍以 `pointIds[]` 为中心。真实旅行包含跨日航班、火车、酒店入住、门票使用日期、签证材料、保险和紧急联系人；缺少这些实体，后续只能不断往 Day 里塞特殊字符串。  
**对策**：显式 `ItineraryItem` 类型与 `Reservation/TransitLeg/Document` 实体。

### B4. 平台目标缺少“真实完成一次旅行”的验证指标

生成计划数、点位数、星标都不是核心价值。若没有人用一份计划完成真实旅行，功能清单再长也不能证明平台成立。  
**对策**：北极星改为“完成且被实际执行/复用的可信行程数”；每次迭代用真实旅程验收。

### B5. 隐私不是分享按钮，而是数据编译边界

行程天然包含家庭住址、酒店、航班、护照、费用、实时位置和同行者。静态页“访问码”若只隐藏 UI，并不能保护已嵌入的数据；已下载的离线包也无法远程撤回。  
**对策**：私有完整版与公开版从同一事实源编译；公开字段白名单、敏感字段禁出、静态扫描与下载前预览；需要保密时使用真正的加密，而不是访问码错觉。

### B6. “单文件 HTML + 离线地图 + 访问码”的技术承诺需拆解

单个 HTML 可嵌入数据与 SVG 图，但完整栅格瓦片包通常需要多文件/Cache Storage；`file://` 或 blob 页面也不能等价获得 PWA Service Worker 能力；OSM 瓦片政策不允许大规模预下载。  
**对策**：区分三种产物：轻量单文件路书、带 SW 的在线 PWA 行程包、可导入 Organic/OsmAnd 的 GPX/KML；默认用示意图 + GPX，不承诺栅格瓦片离线。

### B7. 数据版权、代码许可与人物照片授权尚未进入领域模型

TREK/AdventureLog 的 AGPL/GPL 与未声明许可项目不能当作自由代码库复制；文学引文、网络图片、点评数据和人物照片也都有传播边界。  
**对策**：保留来源与许可字段；参考思想、重写实现；公开分享前做授权检查与必要 attribution。

### B8. 通用导航与后台轨迹是高投入陷阱

通用路网、全球地图、后台定位、电池优化不是小团队短期优势；Polarsteps 级后台轨迹还涉及显著隐私风险。  
**对策**：优先标准导出与外跳；行中用手动打卡、照片 EXIF、可选 GPX/Immich 导入形成实际时间线。

### B9. 行程变更的语义尚未定义

改出发日期时，酒店和航班是否一起移动？删除点位时，关联费用与笔记怎么办？成员退出后历史分摊保留吗？TREK 的大量细节说明，真正困难的是这些边缘语义。  
**对策**：在写 UI 前先写领域规则、反例和迁移策略。

### B10. 小项目质量门强，但产品回归与开发体验落后

地图质量门完善，计划却可重复排点；构建全绿但开发服务器不可用；文档数字依赖手改。  
**对策**：把质量门从“数据正确”扩到“领域行为正确”和“开发者能按文档跑起来”。

### B11. 本地优先不等于 localStorage 永远够用

localStorage 适合小型偏好和早期草稿，不适合大量照片、版本历史、离线路网、事务与多设备同步；移动端还可能被系统清理。  
**对策**：结构化数据逐步迁移 IndexedDB；附件走独立对象存储/Immich；服务端同步保持可选，不强迫公开私有旅行；提供完整导出与恢复演练。

### B12. 运营模型比功能开发更容易被忽略

谁复核开放时间？多久复核？用户报错如何进入队列？AI 成本多少？数据源失效怎么降级？如果这些问题没有负责人和 SLA，平台上线即开始腐化。  
**对策**：每城市设数据健康页、复核队列、来源状态和停止维护机制；允许“未知”，不以补齐率为唯一 KPI。

### B13. 忽略中国出境游的基础设施差异

俄罗斯/中亚的支付、网络、签证、移民卡、落地登记、语言、铁路、时区与现金场景，现有产品几乎都按“信用卡 + 英语 + 西欧”假设设计。  
**对策**：把 `visa/payment/safety/transport/language` 做成 Assertion 类型与行前清单；提供送签级行程单、Yandex/2GIS 深链、卢布/坚戈多币种分账。

### B14. 忽略同行者的“低安装摩擦”协作

同行者不想注册、不想装 App；微信群分享链接、投票、分工、AA 结算，比“邀请注册 + 实时协作”更现实。  
**对策**：guest member、异步投票/评论、任务分派、费用分摊与结算；不做实时协同编辑。

### B15. 忽略创作者与复用工作流

当前只有“站长生产内容”，没有“私有母版 → 公开脱敏 → 他人复用”的路径；626 点无法随创作者增长。  
**对策**：RouteTemplate + ShareProfile + 复制为新 Trip；保留 attribution/license；先服务站长与少数朋友，不急于做市场。

### B16. 忽略可访问性、多语言与低端设备

地图交互对长辈不友好；现场需要俄语/英语地址；低端安卓机、弱网、存储不足都未测试。  
**对策**：大字模式、高对比、键盘/读屏标签；中文为主、俄语/英语地址与短句；性能预算与弱网测试。

### B17. 忽略 AI 的成本与质量运营

现有台账只算调用量/token；没有“每次完成行程成本”“建议接受率”“幻觉数”。  
**对策**：AI 只做语义理解、内容辅助、解释；确定性引擎负责可行性；每次调用记成本与结果来源；建立幻觉与拒绝率指标。

### B18. 忽略故障与应急场景

迷路、丢护照、生病、罢工、天气、支付失败、手机没电——这些才是行中最需要平台的时刻。  
**对策**：离线“今日卡片”包含下一项、票据摘要、紧急电话、使馆、医院、警察、语言短句；不依赖网络。

## 7. 创新机会组合（含边界与验证方式）

> 以下均为“差异化组合候选”，不断言全球首创。优先级以现有资产复用、用户价值、数据可行性、维护成本共同判断。

### F1. 可信行程编译器（最高优先级）

**概念**：把点位、预订、开放日历、交通和个人约束编译成可执行时间线；AI 只理解意图，确定性规则负责排程，独立校验器重新验算。  
**独特处**：每个结论附证据与未知状态；不可行时给出冲突原因和最小修改建议，不“圆谎”。  
**前置**：Trip v2、莫斯科样板数据、真实交通矩阵。  
**验证**：28 条真实动线作基准；无未知点、无重复、无时间重叠；人工认可率与修改成本达标。

### F2. 计划—实际双时间线（最强长期复利）

**概念**：保留原计划、临时调整和实际到访；用真实停留、步行、排队和拍摄时间校正下一次规划。  
**为什么有潜力**：通用产品多关注“计划前”，很少把个人执行偏差变成可解释、可控制的本地偏好模型。  
**隐私**：原始轨迹默认本地，只保存用户确认的统计画像。  
**验证**：连续两次旅行后，系统对停留/通勤估计误差下降，而不是只生成年度海报。

### F3. 行程韧性引擎 / 一键 Plan B

**概念**：闭馆、下雨、延误、体力下降时，不重写整份旅行，只局部修复受影响的时间段，并说明代价：牺牲哪个点、增加多少路程、保留哪些必去项。  
**与 FloatTrip 的差异**：已有真实动线和第一方内容作为骨架；关注行中变更而非一次性生成。  
**验证**：预设 20 个故障场景，修复后硬约束仍 100% 成立。

### F4. 可脱敏的离线旅行胶囊

**概念**：一次导出包含行程、地点知识、轻量示意地图、预订摘要、清单和紧急信息；公开版自动剥离证件号、详细住宿、费用、私人笔记和精确位置历史。  
**差异化**：不是“分享一张页面”，而是可执行、可离线、可选择披露范围的旅行单元。  
**边界**：不承诺已下载内容可撤回；访问码不等于加密；默认用 SVG/GeoJSON 示意地图 + GPX，不批量缓存 OSM 栅格。  
**验证**：飞行模式完成“看下一项→导航外跳→打卡→查看票据摘要”；公开包敏感词扫描零命中。

### F5. 送签级行程单与出境基础面板（俄罗斯/中亚楔子）

**概念**：从 Trip 一键生成签证/邀请函/移民卡/登记所需的行程单（中/英/俄），校验酒店覆盖、往返交通、保险、日期一致性；同时提供支付、网络、eSIM、现金、Mir/UnionPay、使馆/急救、常用俄语短句。  
**差异化**：把“内容”变成“可送签、可入境、可应急”的交付物；现有产品几乎不做。  
**前置**：Document/Reservation/Task 实体；国家/城市级合规事实卡。  
**验证**：用一次真实俄罗斯行程，输出被签证材料接受；错误/缺项可解释。

### F6. 同行者异步决策层

**概念**：分享链接即可参与，无需安装/注册；对候选点投票、认领任务、评论、AA 记账与结算；结果回写 Trip。  
**差异化**：不拼实时协作，拼“微信群里的低摩擦共识”。  
**前置**：guest member、ShareProfile、Expense 分摊；服务端最小同步或链接内编码。  
**验证**：3–6 人真实旅行完成一次投票 + 分工 + 结算；无账号成员可参与。

### F7. 地点—文本—照片互文图谱

**概念**：把建筑、文学引文、历史事件、个人笔记与实拍照片连接到地点和具体行程，不只作为地图弹窗，而能成为主题路线与导览。  
**差异化**：本项目的内容研究方法和自有数据是核心资产。  
**边界**：文学引文和图片需要版权/许可记录。  
**验证**：先做 20 个高质量节点与 1 条可离线导览路线，验证读完率与路线复用，而非追求数量。

### F8. 摄影优先的行程目标（白夜/极昼是俄罗斯的天然场景）

**概念**：将机位朝向、光线偏好、排队、体力与其他日程联合优化；延误时自动判断“保机位还是保景点”；白夜/极昼/冬季短日照进入约束。  
**差异化**：与真实行程联动，而非再做一个太阳计算器。  
**前置**：少量高质量机位字段，不从 highlight 批量猜测后当成事实；与 PhotoPills/PlanIt 交叉验证。  
**验证**：选 10 个熟悉机位，与实地结果及专业工具交叉核对。

### F9. 数据新鲜度运营台

**概念**：每个事实带来源、采集时间、有效期、复核周期；过期/冲突/未知进入统一队列；公开 UI 用一致状态语言。  
**差异化**：把 ticket-monitoring 的 prov/四态迁移到旅行事实，而不是靠人工记忆。  
**验证**：模拟来源失效、冲突和空结果，系统不生成伪确定内容；任一评分/票价/开放时间可追溯。

### F10. 创作者工作流

**概念**：私有母版 → 公开脱敏路书/RouteTemplate → 他人复制为新 Trip；保留 attribution/license；朋友投稿变成“事实修订建议”。  
**差异化**：626 点从“站长内容”变成“可复用的平台资产”。  
**边界**：早期不做市场/分成；先服务站长与少数创作者。  
**验证**：一条公开路线被 3 个不同用户复制并完成；原作者可看到复用数据（匿名聚合）。

### F11. 今日卡片与应急模式

**概念**：离线大字号卡片：下一项、时间缓冲、中文+西里尔地址、导航深链、票据摘要、紧急电话/使馆/医院、常用短句。  
**差异化**：行中最需要的不是“完整行程”，而是“现在做什么”。  
**验证**：飞行模式、锁屏/低电量场景完成核心任务；长辈可独立使用。

### F12. 行程体检（Travel Health Check）

**概念**：出发前检查护照有效期、签证、保险、机票/酒店确认、离线包、现金/支付、网络、紧急联系人、每日负载；行中检查延误/闭馆/超时；行后检查费用/回忆/回流。  
**差异化**：把“旅行准备”从散落清单变成可执行的状态机。  
**验证**：一次真实旅行中，体检发现的缺项在出发前全部关闭；无误报疲劳。

## 8. 明确不建议投入的方向

1. **不做 OTA、自动支付、机票爬虫平台**：合规、信任和维护成本远高于当前收益。
2. **不重造全球离线地图/通用导航**：先标准导出和集成；不批量缓存 OSM 栅格。
3. **不做实时多人协同编辑**：先做分享、投票、评论和异步分工。
4. **不做 23 语言、插件市场、K8s、SSO**：当前用户规模不需要。
5. **不为了“AI 平台”接入更多模型**：先把上下文、约束、验证与成本闭环做好。
6. **不追求 626 点所有字段同时补齐**：先完成高频、可排程点位的深度。
7. **不把“全球首创”当验收标准**：真实复用、可信与可执行才是。
8. **不做后台持续轨迹监控**：隐私与电池成本高，手动打卡 + 照片 EXIF + 可选 GPX 足够。
9. **不做双管线/双 schema**：Travel-Plan-Page 的 lite/canonical 分叉已经证明会留下真实漏洞。
